# 14 — Сборка на новом проекте

Глава из двух частей. **Часть А** — развернуть базу харнеса пошагово: от трёх
вопросов владельцу до первой задачи, прогнанной через весь цикл. **Часть Б** —
вырастить поверх базы СВОИ правила: методика добычи улик, превращения их в
правила и проверки полноты.

Порядок именно такой: база без своих правил — пустая рама, свои правила без
базы негде закрепить.

# Часть А. Развернуть базу

Порядок шагов важен: каждый следующий опирается на предыдущий.

## Шаг 0. Решить три вопроса с владельцем

До любой настройки. Ответы определяют всё остальное.

1. **Где владелец читает результат?** Терминал / мессенджер / дашборд. Если
   не терминал — интерактивные подтверждения и всплывающие вопросы
   выключаются полностью, и нужен канал (см. [02-РАБОТА-С-ВЛАДЕЛЬЦЕМ.md]).
2. **Насколько автономен агент?** Владелец присутствует и отвечает — обычный
   режим прав. Владелец только принимает результат — полная автономия и
   жёсткие гейты вместо разрешений.
3. **Что нельзя нарушать никогда?** 2–4 инварианта проекта. Агент должен
   узнавать их за первые 30 секунд сессии.

## Шаг 1. Файл правил проекта

Скопировать `templates/CLAUDE.md`, заполнить: обзор проекта, стек, инварианты,
команды выката, карту документации.

Проверка: новая сессия, прочитав только этот файл, знает **что за проект,
чего нельзя, как выкатывать и куда писать**. Правила без команды проверки не
писать — см. [13-УСТРОЙСТВО-И-КОНФИГУРАЦИЯ.md].

## Шаг 2. Канал связи и правила общения

Настроить канал, зафиксировать адресата в памяти агента. Записать в память
факты из [02-РАБОТА-С-ВЛАДЕЛЬЦЕМ.md]: подтверждение ≤30 секунд,
«анонсировал — продолжай», никаких интерактивных подтверждений, куда
отвечать, честность отчёта.

## Шаг 3. Память

Завести каталог памяти с указателем и таблицей «когда → что проверить»
(см. [03-ПАМЯТЬ.md]), первые записи — из `templates/memory-example.md`:
как общаться с владельцем, планка кода, разница «тест зелёный / сделано»,
запреты на команды из [11-ЛОВУШКИ.md].

Плюс файл состояния в корне репозитория, подключаемый в контекст каждой
сессии, и журнал работ по месяцам, который **не** подгружается.

**Сразу завести потолок и гейт**: файл состояния ограничен по размеру,
проверка в pre-commit (`templates/check-context-hygiene.py`). Без гейта файл
состояния вырастает на порядки и едет в контекст каждой сессии целиком —
правило вытеснения без гейта не держится, проверено.

## Шаг 4. Гейты

1. `templates/pre-commit-hook.sh` — **единственный источник истины по
   гейтам**. Отдельного файла-описания не заводить: он разойдётся с хуком, и
   читать его не будет никто.
2. Симлинк в `.git/hooks/pre-commit`.
3. Рабочие каталоги задач — в `.gitignore` **кроме** конфигурации гейтов и
   истории ревью: история контрактов и ревью — это улики для Части Б, терять
   их дорого.

Две ошибки, которые не надо повторять:

* **В pre-commit ставить быстрый прогон** (по затронутому модулю), полный —
  перед выкатом. Полный прогон на каждый коммит — главный источник трения:
  десятки минут на коммит убивают темп и провоцируют обходы гейта.
* **Тестовая база — своя на прогон** с первого дня. Одна общая база с
  очисткой таблиц = ложные падения при любых двух параллельных прогонах, и
  отладка исправного кода.

## Шаг 5. Выкат одним скриптом

`templates/deploy.sh`: собрать → миграции → дождаться живости → снимок
карты → сверка. Ручной последовательности команд быть не должно: она
выполняется не полностью. Плюс `templates/check-secrets.sh`; секреты — вне
вебрута. Ворота выката — [09-ВЫКАТ.md].

## Шаг 6. Карта разработки

Минимальная версия, достаточная на старте (полная — [07-КАРТА-РАЗРАБОТКИ.md]):

1. манифест из `templates/dev-map.yaml`: 3–5 направлений, задачи, статусы,
   **обязательное человеческое описание** каждой задачи;
2. тест-гейт схемы манифеста — иначе кривой манифест доедет до прода;
3. трейлер с идентификатором задачи в каждом коммите разработки;
4. страница-дашборд на своей инфраструктуре;
5. сверка + самопочинка пропусков (`templates/devmap-selfheal.sh`), вызов из
   выката.

Единицы объёма, кривые скорости, прогнозы — потом, если понадобится.

## Шаг 7. Хуки — самый недооценённый шаг

Хуки исполняет оболочка, а не модель: это единственный способ автоматического
поведения. Готовые файлы — `templates/hooks/`, ставятся копированием в
репозиторий; после установки — **обязательный прогон** тестов сторожа
(`templates/hooks/test_guard_bash.py`).

Три хука базового набора: состояние на старте сессии, сторож опасных команд,
напоминание о хвостах в конце (подробно и с найденными дефектами —
[13-УСТРОЙСТВО-И-КОНФИГУРАЦИЯ.md]).

**Список запретов писать под свои грабли**: запрет заводится под уже
случившийся отказ, не под воображаемый. Хук — такой же код: проверяется
красным и зелёным, тесты живут в файле.

## Шаг 8. Плагины и инструменты

Минимум: набор навыков-процессов + канал связи + браузер для живой проверки.
Плюс автоматическая память, если владелец не читает терминал: она
восстанавливает погибшую сессию без участия человека (цена — сотни МБ).

Перед установкой чего-либо ещё — раздел «Инструменты» в
[13-УСТРОЙСТВО-И-КОНФИГУРАЦИЯ.md]: половина популярных наборов дублирует
встроенное; ставить по одному и перемерять по журналу вызовов через месяц.

## Шаг 9. Первая задача как проверка харнеса

Взять маленькую реальную задачу и прогнать **весь** цикл: спека → ревью
спеки → план → тест до кода → гейт → выкат → живой смоук → отчёт → память →
карта (см. [05-ПАЙПЛАЙН.md]).

Цель — не задача, а обнаружение мест, где цикл рвётся. Рвётся обязательно.

## Чек-лист готовности

- [ ] файл правил проекта есть, инварианты записаны
- [ ] канал связи работает, правила общения в памяти
- [ ] указатель памяти + таблица условий + первые факты
- [ ] файл состояния с потолком + журнал работ отдельно
- [ ] проверка гигиены контекста в pre-commit
- [ ] гейты + pre-commit (быстрый прогон); полный — перед выкатом
- [ ] тестовая база изолирована по прогону
- [ ] выкат одним скриптом, полный; проверка секретов
- [ ] файл известных проблем заведён
- [ ] карта разработки + трейлеры + сверка + самопочинка
- [ ] свои хуки: состояние на старте, сторож команд, напоминание в конце —
      **с прогоном тестов**
- [ ] полный цикл прогнан на одной реальной задаче

## Чего НЕ переносить

Честный список того, что в исходных проектах прижилось, но повторять не
стоит:

| что | почему |
|---|---|
| полный прогон тестов в pre-commit | десятки минут на коммит — главный источник трения |
| одна тестовая база на все прогоны | постоянные ложные падения |
| журнал/передача без ограничения размера | тысячи строк в контексте каждой сессии |
| две памяти рядом | старая осиротела и молча разошлась с реальностью |
| дюжина плагинов | накопление, а не выбор; хуки каждого — оверхед в каждом ходе |
| рабочие каталоги задач целиком в `.gitignore` | история ревью и контрактов теряется |
| ревью всеми ролями подряд | правке вёрстки не нужен ревьюер безопасности |
| отсутствие линтера | типы и тесты не заменяют стилевой гейт |
| порог-гейт по числу от модели-судьи | оценка судьи скачет на неизменном входе; критерий — счётный (нет находок critical/major), см. [12-РАБОТА-С-МОДЕЛЯМИ.md] |

# Часть Б. Выращивать свои правила

База из Части А — это форма. Живым харнес делают правила, выращенные из
СВОЕЙ истории. Наш пакет здесь полезен как образец формы и как чужой опыт:
грабли типовые, поэтому правила часто совпадут. Но **в этом пакете улики
намеренно очищены до универсальных «почему»** — конкретные даты, числа и
имена убраны при слиянии. Такое «почему» объясняет механизм беды, но не
имеет веса вашей истории. Поэтому новый проект **обязан накапливать свои
улики с первого дня**: правило без вашего случая — чужая мудрость, её
отменяют первой.

## Что должно получиться

Набор, где каждое правило отвечает на четыре вопроса:

1. **что делать** — формулировка в одну-две строки;
2. **почему** — конкретный случай из ВАШЕЙ истории, с числами и датой;
3. **когда срабатывает** — наблюдаемое условие, по которому агент узнаёт
   ситуацию в момент действия;
4. **чем проверяется** — команда, тест или прибор, ловящий нарушение.

Правило без пункта 2 через месяц выглядит вкусовщиной и отменяется первым.
Без пункта 3 — молчит именно тогда, когда нужно. Без пункта 4 — живёт до
первого забывшего.

Набор растёт от каждого разбора; первый заход даст немного — это нормально.

## Этап 1. Добыть улики

Правила не сочиняются, а извлекаются. Источники по убыванию ценности.

**1.1. История исправлений.**

```bash
git log --oneline --grep='fix\|hotfix\|revert\|откат' -i --since='6 months ago'
git log --oneline --diff-filter=D --since='6 months ago'    # что удаляли
git log -S 'TODO\|HACK\|WORKAROUND' --oneline
```

Ищите не правки, а **повторы**: один дефект, починенный дважды, — правило;
трижды — правило, оформленное проверкой. Важно: прогонять **за все месяцы**,
а не за последнюю неделю. Пакет, собранный по свежей памяти, смещён к
последним дням, а случаи ранних месяцев к этому времени кажутся
самоочевидными и потому не записаны — повторы видны только на длинном окне.

**1.2. Разговор с владельцем.** Самый ценный источник и самый
скоропортящийся. В истории переписки искать: где владелец **поправил**
агента; где **переспросил** (переспрос почти всегда указывает на пробел);
где **раздражён** (там правило, нарушавшееся не раз); прямые формулировки
(«всегда…», «никогда…»). Каждое место — кандидат в запись с датой и
дословной цитатой.

**1.2.1. Спросить владельца о его правилах одной строкой.** У владельца
почти всегда есть одно-два правила, сформулированных коротко и жёстко.
Спросить прямо: «какие у вас есть правила про то, как я должен работать и
писать код?» — и записать **дословно, с датой**. Толкование пишет агент, но
заголовком остаётся фраза владельца: дата и авторство дают правилу вес в
споре. Проверка, что шаг сделан: в наборе есть раздел, начинающийся с
закавыченной фразы владельца, а не с пересказа.

**1.3. Аварии и оповещения.** Для каждой аварии: что сломалось, как узнали
(сами или от владельца — второе хуже), что чинили, **какой механизм не дал
бы повториться**.

**1.4. Опись репозитория.** Самый скучный и самый результативный шаг:

```bash
ls scripts/ | cat            # каждый скрипт = чья-то боль в прошлом
ls docs/*.md | cat           # каждый документ = чей-то разбор
crontab -l                   # что делается регулярно и почему
cat .github/workflows/*.yml  # что проверяется перед вливанием
```

Для каждого файла: **какую боль он лечит и записана ли она словами?** Скрипт
есть, а правила нет — знание живёт в одной голове.

**1.5. Комментарии «почему» в коде.** Комментарий, объясняющий причину, —
записанная улика; объясняющий, что делает строка, — мусор.

## Этап 2. Превратить улики в правила

Карточка на каждую находку:

```markdown
**когда:** <наблюдаемый признак в момент действия>
**цель:** <что перестанет ломаться>

<что случилось, с числами и датой; что делать вместо>

**пересмотр:** <при каком условии правило пора менять>
```

Три проверки перед тем, как оставить правило:

* **Условие наблюдаемо?** «Когда пишу важный код» — не условие. «Когда третья
  правка одного места не сдвинула замер» — условие.
* **Улика конкретна?** «Бывали проблемы с памятью» — не улика. «Своп почти
  полон, держатель — один процесс, живущий месяц» — улика.
* **Есть чем проверить?** Если нет — правило живёт словами, но в «пересмотр»
  записывается, чем его планируется проверять.

Разложить по группам (рыба — состав этого пакета: владелец, принципы, память,
передача контекста, пайплайн, сервер, выкат, надёжность, приборы, ловушки,
модели). **Правило не переносится в чужой проект, если у вас его причины
нет** — не берите чужие числа: другой сервер, другой стек, другие грабли.

## Этап 3. Поднять память до механизма

Одних файлов мало (см. [03-ПАМЯТЬ.md]):

1. указатель, который грузится сам каждую сессию;
2. в начале указателя — таблица «когда → что проверить»;
3. правило без строки в таблице — недоделанное;
4. ежемесячная ревизия: по каждой молчащей записи агент предлагает решение,
   владелец подтверждает списком.

Проверка, что механизм жив: взять последние три ошибки агента и найти строку
таблицы, которая должна была сработать. Не нашлась — это и есть недостающие
правила.

## Этап 4. Оформить проверками то, что можно забыть

Типовой минимум, окупающийся почти везде:

| правило | во что превращается |
|---|---|
| у сервиса потолок памяти и политика перезапуска | скрипт-сторож (`templates/server_hygiene_check.py`) + шаг в CI |
| порты наружу только разрешённые, поимённо | тот же сторож |
| не выкатывать поверх идущей работы | ворота выката (`templates/deploy_guard.py`) |
| брошенные задачи закрываются | фоновая задача раз в час |
| перед выкатом есть откат | тег образов + снимок базы + автооткат по живости |
| секреты не в репозитории | grep-проверка в CI (`templates/check-secrets.sh`) |
| работа не проходит мимо карты | сверка истории + самопочинка (`templates/devmap-selfheal.sh`) |

**Каждую новую проверку доказать на заведомо больном случае** — иначе её
молчание неотличимо от порядка. Пороги вынести в переменные, чтобы больной
случай строился без ожидания суток. Где возможно — идти на шаг дальше
проверки: **починка, которая происходит**, вместо проверки, которая падает
(образец — самопочинка карты, [07-КАРТА-РАЗРАБОТКИ.md]).

## Этап 5. Проверить полноту

1. Выписать ВСЕ скрипты, документы, регулярные задачи и проверки CI;
   напротив каждого — файл набора, где практика описана. Пустая клетка —
   пропуск.
2. Пройти по памяти агента: каждая запись либо перенесена в набор, либо
   помечена «только для этого проекта».
3. Вопросы, на которые набор обязан отвечать (нет ответа — пропущен пласт):
   * Что делать, когда упал прод? Кто и как откатывает?
   * Как понять, что выкат безопасен прямо сейчас?
   * Где лежат секреты и как ротируются?
   * Что происходит с работой при перезапуске сессии агента?
   * Как узнать, что «стало лучше», а не «кажется лучше»?
   * Сколько стоит одна операция и где утекают деньги?
   * Что делать, если владелец недоступен, а задача заблокирована?
   * Какие проблемы известны и не требуют расследования?
   * В каких форматах пишет владелец и умеет ли агент читать каждый?
   * Что работает **мимо** основного способа запуска (процессы вне
     контейнеров, расширения агента) — видит ли это проверка гигиены?
   * Что **доставляет** результат молча — проверяется ли факт доставки?
   * Что установлено и ни разу не вызвано — нет пользы или нет условия
     срабатывания? (см. [13-УСТРОЙСТВО-И-КОНФИГУРАЦИЯ.md])

Про каждый ответ спросить отдельно: **это проверено или это замысел?** Самые
дорогие пропуски находятся не прибором, а вопросом владельца («что ещё ты мог
пропустить?», «проверь, работает ли это вообще») — механизм может стоять на
месте и молча не работать.

## Этап 6. Отдать так, чтобы это читали

* Файлами в репозитории, а не в переписке: что живёт в чате — теряется.
* Один файл — одна тема, 100–200 строк. Больше не читают.
* Первым — файл про работу с владельцем: несостыковки в общении дороже
  технических ошибок.
* Указатель в начале: что где лежит и в каком порядке читать.
* Уметь собрать одним файлом целиком — удобно отдать другому агенту в
  контекст. Сборщик проверяет полноту **в обе стороны**: всё нужное вошло
  дословно, и ничего лишнего (байткод, кеши, окружение) не вошло — лишнее
  проверяется прогоном по составу архива, а не глазами.

## Чего не делать

* **Не переписывать этот пакет своими словами.** Правило без вашей улики не
  работает.
* **Не сочинять правила «на будущее».** Правило без случая — догадка.
* **Не превращать в устав.** Набор нужен, чтобы работать быстрее и не
  наступать дважды, а не чтобы им отчитываться.
* **Не оставлять правило без владельца.** У каждого — либо проверка, которая
  его сторожит, либо строка в таблице условий. Иначе через месяц оно мёртвое.

## С чего начать прямо сейчас (первые два часа)

1. `git log --grep='fix|revert' -i` за полгода → 10 повторяющихся дефектов.
2. 5 мест в переписке, где владелец поправил агента → 5 правил с цитатами.
3. 3 самые дорогие аварии: как узнали, что чинили, чем не дать повториться.
4. Указатель памяти с таблицей условий → внести эти ~15 правил.
5. Прогнать по своему серверу чек-листы [10-СЕРВЕР-И-НАДЁЖНОСТЬ.md] и
   [09-ВЫКАТ.md] командами — что не выполняется, то и есть первый список
   работ.

Дальше набор растёт сам: каждый разбор дефекта заканчивается вопросом «какое
правило не дало бы этому повториться» — и ответ становится записью.
