# 07 — Карта разработки (dev-map)

Карта разработки показывает владельцу состояние всей работы: направления, задачи,
готовность, скорость, хронологию, что ждёт его проверки и что дальше по плану.

**Зачем это в харнесе:** владелец не читает диффы. Без карты вся работа для него невидима,
и единственный способ узнать статус — спросить агента, то есть поверить на слово. Отчёт в
<канале связи> читается один раз, а статус живёт: карта переводит разработку в форму,
которую владелец читает сам, когда захочет. Отдельно она решает судьбу состояния «сделано,
но не проверено живым прогоном»: без карты оно живёт строкой в одноразовом отчёте и тихо
превращается в «сделано»; на карте оно копится и видно, пока владелец его не разгребёт.

---

## Устройство

```
dev-map.yaml (манифест — ИСТОЧНИК ИСТИНЫ, коммитится в репозиторий)
      ↓
verify (предикаты авто-подтверждения: файл существует / миграция применена /
      ↓  эндпоинт отвечает / тест зелёный)
коллектор (планировщик ежедневно + принудительно при деплое) → снимок в таблицу
      ↓
эндпоинт отдаёт статический HTML со впечатанными данными снимка
```

Модули держать разделёнными: расчёт объёма работы и расчёт времени/скорости — чистое ядро
без инфраструктурных импортов (переносится между проектами как есть); схема манифеста —
отдельный модуль, на ней держится тест-гейт; сверка git-истории и предикаты — отдельно.

Скелет манифеста — `templates/dev-map.yaml`.

---

## Модель статусов

Готовность направления = **среднее % по его задачам**.

| Статус | Значение | % |
|--------|----------|---|
| `done` | готово И протестировано владельцем | 100 |
| `test` | сделано агентом, ждёт живого теста владельца | 90 |
| `wip` | дорабатывается | % по чек-листу |
| `plan` | не начато | 0 |

**Правило, которое делает карту честной:** завершённую агентом, но не протестированную
владельцем работу ставить `test`, не `done`. Живой тест — последние 10%, и делает их
человек. Без этого правила карта показывает 100% там, где никто ничего не проверял.

**Обратная сторона того же правила:** у задачи есть флаг `owner_testable`. Внутренняя
работа — переборка кода, гейты, инструменты самого агента — владельцу недоступна для
проверки, и статус `test` ей **запрещён гейтом**: она идёт сразу в `done`. Иначе панель
«ждёт живого теста» наполняется строками, с которыми владелец ничего сделать не может, и
обесценивается целиком — тем же механизмом, которым вечно красные ложные цели обесценивают
алерты. Вскрывается это вопросом владельца «не понял, какой проверки она ждёт» — когда
заметная доля ожидающих задач оказывается непроверяемой в принципе.

## Единица измерения — ЕР

Проценты обманывают: «80% готово» ничего не говорит об оставшемся объёме. Поэтому объём
меряется в **ЕР (единицах разработки)**.

У каждой задачи есть `volume: { loc, complexity, tokens_k, estimated }`:
- `loc` — строки кода (считаются скриптом по git-трейлерам),
- `complexity` — 1–10 по рубрике из спеки,
- `tokens_k` — честная ручная оценка расхода,
- `estimated: true|false` — оценка или факт.

Формула:
```
V_dev  = 0.35·ln-норм(loc) + 0.35·(cx / c_ref) + 0.30·ln-норм(tokens_k)
V_test = 0.2 · V_dev
V_total = 1.2 · V_dev
```

**Калибровка ФИКСИРОВАНА и выбрана навсегда:** эталон — рыночная средняя задача ИИ-кодинга
`loc_ref: 500, c_ref: 4, tokens_ref_k: 300`.

**Почему фиксирована:** плавающая калибровка от средних проекта немонотонна — закрытие
крупной задачи поднимает средний масштаб и **роняет** показатель «Сделано». Ре-калибровка
допустима только явным решением и с пересчётом всей истории. Средние проекта — отдельная
метрика «характер проекта», не калибровка.

## Манифест

```yaml
version: 1
calibration: { loc_ref: 500, c_ref: 4, tokens_ref_k: 300, set_at: "market" }
unattributed_loc: <число>   # вся история до внедрения трейлеров — отдельной строкой, честно

milestones:
  - { id: ms.start, date: "YYYY-MM-DD", label: "Старт проекта",
      summary: "Что произошло, словами владельца продукта." }

queue: [<id>, <id>]          # «Дальше по плану», только id задач

layers:
  - { id: product,  label: "Продукт",        color: "#2b9bd6" }
  - { id: platform, label: "Платформа",      color: "#8b6cf0" }
  - { id: infra,    label: "Инфраструктура", color: "#5aa06a" }

lines:
  - id: <направление>
    layer: product
    name: "<Название направления по-человечески>"
    pipeline: true      # приоритетная линия, ИСКЛЮЧЕНА из сумм проекта (двойной счёт)
    tasks:
      - id: <направление>.<задача>
        status: test
        title: "<Что сделано, одной строкой>"
        summary: "Что изменилось и почему — по-русски, БЕЗ жаргона и имён файлов."
        when: { started: "YYYY-MM-DD", done: "YYYY-MM-DD", tested: null, estimated: true }
        volume: { loc: 3200, complexity: 6, tokens_k: 7000, estimated: true }
        checklist:
          - { label: "...", done: true, done_at: "YYYY-MM-DD",
              summary: "...", volume: { loc: 240, complexity: 3, tokens_k: 900, estimated: true } }
        verify:
          mode: soft     # soft: расхождение → флаг, статус НЕ понижается. strict: понижается
```

**Правила заполнения:**
- `summary` **обязателен** у каждой задачи, каждого пункта чек-листа и каждой вехи.
  Держится тест-гейтом. Пишется для владельца продукта: что изменилось и почему это было
  нужно, без технического жаргона и без имён файлов.
- Даты ограничены сегодняшним днём **в часовом поясе владельца** (не UTC — иначе манифест
  принимает завтрашнюю дату вечером, и гейт «дата не больше сегодняшней» пропускает будущее).
- `when`: взял в работу → `started`, завершил → `done`, владелец подтвердил → `tested`.
- Задача, ушедшая в `done`/`test`, удаляется из `queue` при следующей правке.

## Трейлер коммита

Каждый коммит разработки несёт git-трейлер:

```
Dev-Map: <id задачи>
```

По трейлерам считается фактический LOC каждой задачи. Считает **хост-скрипт**, не задача
внутри контейнера — внутри контейнера нет `.git`.

**Формат критичен:** `Dev-Map:` держать в ОДНОМ блоке с остальными трейлерами
(`Co-Authored-By` и т.п.), без пустой строки между ними — иначе git не считает это
трейлером. Сообщение передавать через `git commit -F -`: многострочный `-m` схлопывается
в одну строку.

## Тест-гейт манифеста

Тест в общем suite проверяет: схему; наличие `summary` везде; непротиворечивость дат
(`done ≥ started`, `tested ⇒ done`, `plan` + `done` запрещено); потолок дат по часовому
поясу владельца; единственность идентификаторов; запрет `test` у задач с
`owner_testable: false`; инвариант сумм `made + in_progress + planned == total` —
расхождение здесь означает, что показатель врёт, а глазами это не видно.

Кривой или неполный манифест **не проходит гейт** — то есть не коммитится.

## Самопочинка: пропуск чинится сам, а не докладывается

Главная механика этой системы и главный урок.

**Проблема:** правило «обновляй карту в том же коммите» держится вниманием агента.
Внимание отказывает: владелец получает «за сегодня изменений нет», хотя работа шла весь
день. **Первая попытка (неверная):** запретить коммит без записи в карту. Обходится через
`--no-verify`, то есть не держится.

**Что работает** (скрипт — `templates/devmap-selfheal.sh`):

1. Сверка git-истории с манифестом. Находит два вида пропуска:
   - коммит без трейлера `Dev-Map:`;
   - **коммит с трейлером, но за день которого запись задачи не менялась** — то есть на
     карте этого дня нет.
2. Водораздел (`audit.cursor`) — SHA прошлой сверки, чтобы не пересматривать вечно старую
   историю.
3. Нашла сверка пропуск → **запускается агент с одной узкой задачей**: завести пропущенную
   работу в манифест. Агенту разрешён ТОЛЬКО `dev-map.yaml`, никакого кода.
4. Вызывается из скрипта деплоя. **Деплой — единственный путь, которым код попадает на
   прод**, поэтому проверка там надёжнее любого запрета на коммит. Деплой сверка не
   блокирует: карта не должна мешать выкатке.
5. Крон дублирует ежечасно — на случай дней без деплоя.

**Ключевая деталь, стоившая потери работы:** водораздел двигает **только** скрипт
самопочинки и **только после успеха** агента. Пока курсор двигала сама сверка (до запуска
агента), упавший агент означал потерю пропуска навсегда — коммит уезжал за водораздел и
больше не всплывал.

**Смертельная грабля фонового агента:** запускать его строго с изолированной
конфигурацией — минимальный набор инструментов, **ни одного расширения, держащего канал
связи с владельцем**. Канал с единственным допустимым потребителем (как long-polling у
мессенджер-ботов) фоновый агент отбирает у живого рабочего сеанса — и связь с владельцем
обрывается; ежечасный крон обрывал бы её каждый час. Конкретные флаги изоляции для текущей
оболочки — в [13-УСТРОЙСТВО-И-КОНФИГУРАЦИЯ.md] и в `templates/devmap-selfheal.sh`;
родственные ловушки — [11-ЛОВУШКИ.md].

## Дашборд поверх карты — пульт харнеса

Опциональный слой для владельца, читающего не диффы: страница, где карта видна без
посредника. Манифест и статусы — те же; дашборд только показывает.

Целевая конструкция — **надпроектная** (принята спекой `SPEC_DASHBOARD_V5.md` в корне
рабочей папки; там же критерии приёмки и этапы исполнения): дашборд — не страница одного
проекта, а **пульт всего харнеса**, собирающий данные с нескольких серверов. Устройство в
два слоя:

- **Слой А — эндпоинт данных на каждом проекте.** Проект уже хранит готовый снимок;
  добавляется эндпоинт `GET .../dev-map/data`, отдающий `{ project: {id, name, color, url},
  snapshot: {...} }` с CORS на домен дашборда и кэшем ~5 минут. Логика та же, что у
  страницы: последний снимок, при его отсутствии — расчёт на лету. Коллектор, схема и
  манифест не меняются. **Этот контракт — часть переносимого пакета:** новый проект
  харнеса подключается к пульту, реализовав эндпоинт (~30 строк).
- **Слой Б — отдельное статическое приложение.** Список проектов — в конфиге
  `projects.json` рядом со статикой: добавить проект = одна запись, без пересборки.
  Приложение параллельно опрашивает все эндпоинты; недоступный сервер — карточка «нет
  связи, показан кэш от <даты>» из последнего удачного ответа. Принцип «страница живёт,
  даже когда всё сломано» переносится на уровень каждого проекта.

**Информационная архитектура — один факт живёт ровно на одной странице.** Всё остальное —
счётчики-ссылки. Урок первой версии: мега-главная, дублирующая «сегодня», «ждёт теста» и
ленту, плюс две почти одинаковые хронологии заставляют владельца каждый раз решать «куда
за этим идти». Экранов пять, у каждого одна роль: **Обзор** (портфель проектов карточками:
прогресс, скорость, статус прода, «ждёт теста: N», свежесть снимка; при одном проекте
пропускается), **Проект** («как дела?» одним экраном: статус, KPI-ряд — только здесь,
один график с вехами, таблица направлений с раскрытием задач на месте; статистика —
свёрнутым блоком), **В работе** (текущее + очередь «дальше по плану»), **Тест-план**
(рабочий чек-лист владельца: только ждущее живой проверки, старейшее сверху),
**История** (одна лента вместо хронологии и ленты, с фильтром: всё / статусы / шаги /
вехи; виртуализация обязательна).

**Правило текста на всё приложение:** ни один абзац не показывается развёрнутым по
умолчанию — `summary` обрезается до двух строк и раскрывается кликом. Карточка задачи —
единый компонент на всех экранах. Обучающие блоки «как читать» со страниц убираются в
подсказки-«?» у терминов и одну страницу-справку.

**Производительность — критерии, а не пожелания:** переключение страниц < 200 мс; длинные
ленты виртуализируются; первый экран < 1 с (скелетоны, данные асинхронно); бандл с
потолком размера. Урок: страница без этих критериев доросла до подвисаний вкладки на
десятки секунд, и это нашлось только живым осмотром.

**Мобильная версия — равноправное требование,** не «по остаточному принципу»: нижний
таб-бар, компактные карточки, кликабельное ≥44px.

**Стек** (зафиксирован спекой): сборщик + компонентный каркас с типами, держащими контракт
данных; правило «никаких внешних CDN в рантайме» сохраняется — всё вендорится в бандл,
сборка идёт на хосте, на сервер едет готовая статика. Старая версия живёт параллельно до
живой приёмки владельцем; редирект — только после «принято».

**Откуда данные — снимок, а не расчёт на лету:** коллектор читает манифест, считает
агрегаты и кладёт **готовый JSON** снимком в базу — одна строка на день, перезапись по
дате (коллектор можно гонять сколько угодно, дублей не будет — это делает безопасным вызов
из деплоя). Эндпоинт достаёт последний снимок и впечатывает его в статический HTML одной
строкой; страница самодостаточна, к API не ходит. Следствия: открытие страницы — один
запрос к базе; сломанный манифест **не роняет страницу** (покажет вчерашний снимок);
снимки копятся в историю. Ежедневный прогон — базовый ритм, деплой запускает коллектор
принудительно: владелец видит результат выкатки сразу. Пока снимков нет — эндпоинт
считает на лету, чтобы не было белого экрана в первый день.

**Чем сторожится:**
- **Гейт схемы манифеста** (см. выше) — кривые данные не доезжают до владельца.
- **Предикаты трёхзначные:** `True / False / None`, где `None` = «проверить не удалось».
  Если «не смог проверить» схлопывается в «не сделано», временно лежащий сервис
  превращает готовые задачи в незаконченные — дашборд врёт в самый неудачный момент.
  При `None` берётся статус из манифеста; ошибка одного предиката не роняет сбор снимка.
- **Расхождение — флажком, а не понижением статуса** (`verify.mode: soft` по умолчанию):
  автоматика ошибается чаще человека, ведущего манифест. `strict` — точечно, где предикат
  действительно надёжен. Честный замер зрелого проекта: предикаты покрывали единицы
  процентов задач — **карта держится дисциплиной ведения манифеста и гейтом схемы,
  предикаты — вспомогательная страховка**. Внедрять их после дисциплины, не вместо.
- **Честность про свежесть:** снимку больше двух суток → страница сама говорит «устарело».
  Дашборд, молча выдающий трёхдневную картину за сегодняшнюю, хуже отсутствующего.
- **Никаких внешних ассетов:** css/js вендорены и отдаются со своего домена — страница
  обязана работать без чужих CDN, и чужой код не меняется под ногами.
- **Деградация на старых снимках:** фронт переживает отсутствие любого нового поля, иначе
  выкатка новой версии ломает страницу до первого нового снимка.
- **Подписи из манифеста экранируются** при любой вставке в разметку — иначе название
  задачи становится точкой внедрения скрипта на публичной странице.

## Что переносить в новый проект

**Обязательно:** манифест + модель статусов (включая `test` vs `done` и `owner_testable`),
требование `summary` по-человечески, гейт схемы, трейлер коммита + сверка + самопочинка,
вызов сверки из деплоя. Если проект подключается к пульту харнеса — эндпоинт данных
(слой А выше).

**По желанию (роскошь, дорастает позже):** ЕР, предикаты подтверждения, кривые скорости,
прогнозы, хронология, вехи, очередь, сам дашборд-страница. Порядок именно такой: каждая
следующая вещь имеет смысл, только когда предыдущая обкатана.

**Начинать с малого:** манифест из 3–5 направлений, статусы, summary, трейлеры, сверка.
Этого достаточно, чтобы владелец видел работу.
