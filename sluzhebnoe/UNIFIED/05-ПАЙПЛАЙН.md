# 05 — Пайплайн: от идеи до прода

Уклад, по которому делаются крупные работы. Мелкие правки идут коротким путём —
см. «Глубина по размеру задачи»; уровень выбирается ДО старта и вниз не понижается.

Цепочка целиком:

```
запрос владельца
   → 1. спека → 2. adversarial-ревью спеки (отдельным агентом) → правка спеки
   → 3. план по фазам → 4. контракт на задачу → 5. проход по ловушкам
   → 6. тесты (другими глазами) → 7. код (TDD)
   → 8. ворота качества → 9. ревью кода → 10. коммит
   → 11. выкат → 12. ЖИВОЙ смоук
   → 13. закрытие: отчёт + память + карта разработки
```

Два ключевых положения: **ревью спеки идёт ДО кода** (находки стоят десятки минут
на этапе спеки и дни на этапе кода) и **тесты зелёные — это ещё не работает**:
работает то, что прошло живой смоук.

---

## Глубина по размеру задачи

Не каждая задача стоит всей цепочки. Уровень выбирается до старта и записывается:

| уровень | что это | процесс |
|---|---|---|
| **тривиальная** | опечатка, переименование, флаг конфигурации, ≤10 строк без логики | статический разбор + типы, коммит |
| **обычная** | фича, починка, рефактор одного модуля, ≤300 строк | контракт → тесты → код → ворота → один ревьюер → смоук затронутого |
| **критичная** | безопасность, миграции, деньги, схема, инфраструктура | полная цепочка + три узких ревьюера + полный живой смоук |

При сомнении между обычной и критичной — брать критичную: агенты систематически
недооценивают риск. Некоторые темы критичны независимо от объёма: аутентификация,
платежи, миграции схемы, всё, что трогает секреты.

Честность уклада проверяется числом, а не намерением: сколько спек и планов на
сколько коммитов (`ls specs/ | wc -l ; ls plans/ | wc -l ; git rev-list --count HEAD`).
Спека заводится под работу с ценой ошибки, не под всё подряд — но если спек единицы,
а документ описывает тринадцать звеньев, он описывает намерение, а не уклад, и
честнее это назвать.

## 1. Спека

**Вход:** запрос владельца — бриф, макет, репорт.
**Выход:** `docs/specs/<дата>-<имя>.md`.
**Готово, когда:** каждое утверждение о существующей системе проверено фактом;
статус «СОГЛАСОВАНО» от владельца.

Пишется ДО любого кода. Шаблон — `templates/spec-template.md`. Обязательные разделы:

| раздел | содержание |
|--------|-----------|
| заголовок + источник | откуда пришло, ссылка на макет/бриф |
| статус | «итерация N — после ревью владельца», «ждёт согласования», «СОГЛАСОВАНО» |
| решения владельца | зафиксированы дословно, с датой — единственная защита от «мы же договаривались иначе» через три недели |
| §0 «Отдельно и вперёд» | найденное попутно, что чинится РАНЬШЕ основной работы (обычно обман пользователя или блокер) |
| зачем | проблема словами продукта, не кода |
| что берём / что не берём | таблица решений по каждому элементу. **«Не берём» с причиной — обязательно**, иначе заведут заново |
| целевая архитектура | что появится и как ложится на существующее |
| разделы по механикам | каждая с состояниями, крайними случаями, форматом данных |
| фазы | с оценкой и **критериями приёмки на каждую** |
| бюджет | деньги на внешние сервисы, если работа их тратит |
| проверенные факты | что проверено по коду/базе фактом, а что предположение — помечено раздельно |
| приложение с ревью | находки adversarial-ревью + решение владельца по каждой |

Два правила, спасавшие чаще всего:

* **любое утверждение о существующих данных проверять фактом** — запросом к базе,
  чтением кода. Спека, называющая неверную причину бага, ведёт реализацию чинить не то;
* **критерий приёмки — проверяемый предикат.** Не «страница выглядит хорошо», а
  «замер даёт ноль замечаний, проверка доступности — ноль serious».

## 2. Adversarial-ревью спеки

**Вход:** спека + кодовая база.
**Выход:** документ находок `<имя>-REVIEW.md` с классами CRITICAL / IMPORTANT / MINOR.
**Готово, когда:** все CRITICAL и IMPORTANT закрыты правкой спеки, решение владельца
по каждой находке записано в приложение спеки.

Отдельный агент (сильная модель — см. [12-РАБОТА-С-МОДЕЛЯМИ.md]) читает спеку
**с задачей её сломать**, а не одобрить. Промпт по смыслу: «Вот спека и вот кодовая
база. Найди всё, что неверно, недостижимо, конфликтует с существующим кодом или
сломает работающее. Классифицируй. Не хвали.» Ищет три вещи: что **ломает
исполнение**, что **не сойдётся с существующим кодом**, что **невозможно проверить**.

**Автор спеки не ревьюер собственной спеки.** Даже когда это один и тот же агент —
это отдельный запуск в отдельном контексте.

Типичный улов — 10–25 находок на спеку, и это находки того сорта, который на этапе
кода стоит дней: поле, молча выпадающее на слое валидации; чужой компонент, читающий
удаляемое поле; запись в базу на GET-запросе; тест, который спека предлагала удалить,
а он был единственной защитой сохраняемого поведения; столкновение двух механизмов
версионирования из разных частей системы; критерий, опирающийся на данные, которых
система не собирает.

**Ответ обычно уже в спеке.** Прежде чем спрашивать автора спеки или владельца —
прогрепать спеку целиком, включая решения и приложения. Если ответа действительно
нет — это находка: спека неполна, и вопрос формулируется вместе с предложением,
каким разделом её дополнить.

## 3. План реализации

**Вход:** согласованная спека.
**Выход:** `docs/plans/<дата>-<имя-или-фаза>.md` — по документу на фазу.
**Готово, когда:** каждая задача имеет файлы с путями, интерфейсы, шаги с чекбоксами
и требования к тестам; общие ограничения собраны в шапке.

Шаблон — `templates/plan-template.md`. План — не пересказ спеки, а последовательность
задач для исполнителя:

* **Шапка — общие ограничения**, которые исполнитель обязан знать до первой строки:
  где живёт логика; какие поля НЕ вводить (потому что уже есть); что не трогать;
  как гонять тесты (если набор нестабилен поимённо — сравнивать только полным
  прогоном); чего нет в окружении; язык комментариев; какой трейлер несёт коммит.
* В шапке же — сквозные требования: **тест до кода** и **замер на живом обязателен
  помимо теста** (есть случаи, где зелёные тесты закрепляли неверное допущение).
* Задачи `Task 0..N`, каждая: ссылка на раздел спеки; список файлов
  (изменить/создать) **с абсолютными путями и номерами строк**; интерфейсы (что
  принимает, что отдаёт); шаги с чекбоксами `- [ ]` — план заодно служит трекером;
  **требование к тесту** — что он проверяет и почему (см. шаг 6).

## 4. Контракт на задачу

**Вход:** задача из плана + реальный код.
**Выход:** машиночитаемый контракт, `templates/pretask-template.yaml`.
**Готово, когда:** каждый критерий приёмки проверяется командой с однозначным
выводом; либо стоит флаг «спека неполна».

Перед каждой нетривиальной задачей — отдельный проход **анализа без кода**:

```yaml
task_id: <из плана>
tier: <уровень глубины>
acceptance_criteria:      # булевы предикаты, проверяемые тестом или командой
edge_cases:               # случай → ожидаемое поведение
failure_modes:            # что НЕ должно произойти ни при каких условиях
test_plan: {unit, integration, negative}
out_of_scope:             # что задача НЕ делает
known_dependencies:       # соседние модули: видим, но не правим
risk_flags:               # где вероятнее всего сломается
```

Правила прохода: **не писать код, не предлагать реализацию**. «Работает корректно» —
не критерий; «команда X возвращает 0» — критерий. Если задача описана недостаточно —
остановка с флагом «спека неполна», а не додумывание. Ценность контракта — поймать
расхождение между планом и реальным кодом до того, как исполнитель начнёт писать.

Контракт — источник истины для тестов и кода. Менять его по ходу можно один раз,
с пометкой «пересмотрен из v1» и пересмотром уже написанных тестов — иначе критерии
приёмки подгоняются под то, что получилось.

## 5. Проход по ловушкам

**Вход:** контракт + код; реализацию (если есть черновик) исполнителю НЕ показывают.
**Выход:** три списка: подводные камни этой задачи в этом коде; краевые случаи,
которые легко не заметить; места, где вероятнее всего будет больно.
**Готово, когда:** списки переданы автору тестов и автору кода.

Зачем отдельно от контракта: контракт отвечает «что должно получиться», этот проход —
«обо что споткнёмся по дороге»; он пишется другими словами и другим взглядом, потому
находит другое. Кода и предложений реализации проход не содержит.

---

## 6. Тесты — до кода и другими глазами

**Вход:** контракт + список зависимостей. **НЕ вход:** существующая реализация.
**Выход:** падающие тесты, воплощающие критерии приёмки.
**Готово, когда:** тесты красные, и каждый объясняет причину своего существования.

Правило «автор кода ≠ автор тестов» — самое дорогое в пайплайне и самое окупаемое:
оно ловит случай, когда механизм и его проверка написаны из одного неверного
допущения. Формы две, по глубине задачи:

* **критичная:** отдельный автор тестов, которому реализацию не показывают —
  иначе тесты пересказывают код, а не проверяют требование;
* **обычная:** текст теста пишется в план на этапе планирования, до реализации, —
  исполнитель без готового текста пишет тест под свою реализацию, и тест перестаёт
  быть проверкой. Тест в плане — формализованное требование.

Тест объясняет комментарием сверху, по-человечески, что он охраняет:

```
/**
 * Форма в финале печатала «заявка отправлена», ничего не отправляя (заглушка
 * на боевой странице). Клиент оставлял контакт, видел подтверждение и ждал
 * ответа, которого не будет.
 */
```

Такой тест переживает рефакторинг, потому что понятно, зачем он.

## 7. Код

**Вход:** контракт + тесты + списки ловушек.
**Выход:** зелёные тесты, реализация в границах контракта.
**Готово, когда:** красный → код → зелёный пройден по каждому шагу; полный прогон
без регрессий; ничего вне `out_of_scope` не тронуто.

Порядок жёсткий: **красный тест → код → зелёный.** Автор кода **не имеет права
править тесты**. Тест кажется неверным — оформляется спор (`test_dispute`) с
обоснованием, лимит один на тест.

**Отрицательная проверка:** закладывать в план шаг «временно сломать код и убедиться,
что тест краснеет». Тест, который зелен всегда, — не тест.

Два режима исполнения, оба рабочие:

* **субагентами** (план из 5+ независимых задач): оркестратор раздаёт задачи по
  одной, после каждой — ревью отдельным агентом, потом коммит. Оркестратор не пишет
  код сам, он проверяет;
* **в одной сессии** (1–3 связанные задачи): идёшь по плану сам, но всё равно TDD
  и всё равно ревью перед коммитом.

Правила делегирования:

* главная сессия оставляет себе архитектуру, декомпозицию, сложные решения и
  проверку результатов; механику раздаёт по сложности моделям разной цены
  ([12-РАБОТА-С-МОДЕЛЯМИ.md]);
* **перепроверять работу агентов перед отчётом владельцу** — агенты возвращают
  неточные и приукрашенные результаты;
* агентам — только абсолютные пути; проверять, куда агент записал файл.

Ловушки делегирования, пойманные вживую (полный список — [11-ЛОВУШКИ.md]):

* субагент, запустивший тесты **в фоне** и завершившийся не дождавшись, оставляет
  прогон, бьющий по общей тестовой базе посреди чужих проверок, — десятки ложных
  падений. Инструктировать явно: «foreground, дождись завершения, не завершайся
  до коммита»;
* никогда не инструктировать ждать процесс тесным циклом по PID — субагент уходит
  в бесконечный опрос мёртвого процесса;
* коммитить строго по очереди: `git add` во время чужого `git commit` с долгим
  хуком укладывает файлы в чужой коммит.

## 8. Ворота качества

**Вход:** зелёная реализация.
**Выход:** чеклист ворот, где у каждого — **улика**: путь к логу или вывод команды.
**Готово, когда:** все обязательные для уровня задачи ворота пройдены с уликами.

Набор определяется проектом и глубиной задачи (подробно — [06-ГЕЙТЫ-КАЧЕСТВА.md]):

| ворота | пример | когда обязательны |
|---|---|---|
| тесты | `pytest -q` | всегда, кроме тривиальных |
| статический разбор | `ruff check .` | всегда |
| типы | `mypy .` | всегда, если язык типизирован |
| сборка | `docker compose build <сервис>` | если тронут образ |
| здоровье | `curl -fsS .../health` | если сервис перезапускался |
| миграции | сухой прогон | если добавлена миграция |

Прямо запрещено: помечать «пройдено», не выполнив команду; глушить тесты без явного
флага; менять критерии приёмки, чтобы они сошлись. Самосертификация не считается.

## 9. Ревью кода

**Вход:** дифф + контракт; ревьюер — **не автор кода**.
**Выход:** находки в машиночитаемом виде.
**Готово, когда:** ни одной находки critical/major, либо после двух кругов —
эскалация владельцу.

* Обычная задача — один ревьюер общего профиля.
* Критичная — до трёх узких **параллельно**: безопасность, производительность,
  читаемость; арбитр сводит находки. Каждый смотрит только свою ось — так находки
  не размазываются.

Формат находки:

```yaml
reviewer_role: security
findings:
  - finding_id: F2-sec-01
    severity: major          # critical | major | minor
    location: "путь:строка"
    issue: >-
      Что именно не так, с механикой отказа.
    rule_ref: "CWE/PEP/правило линтера/пункт спеки — для critical и major обязательно"
    reproducer: >-
      Конкретные шаги/вход, приводящие к отказу.
    suggestion: >-
      Минимальная правка, закрывающая проблему.
```

Требования к находкам: **воспроизводимый сценарий отказа**, а не «выглядит хрупко» —
находка без сценария отбрасывается; critical/major — со ссылкой на правило, minor —
с текстовым обоснованием. Это отсекает «мне так кажется» там, где решение дорогое,
и сохраняет интуитивные замечания там, где дёшево.

Два жёстких правила выхода из цикла:

* **предел — два круга ревью на задачу.** Не сошлось — вопрос владельцу, а не третий
  круг: дальше двух кругов расходятся не факты, а вкусы;
* **порог по числовой оценке модели-судьи не ставить.** Оценка одного и того же кода
  скачет между прогонами; гейт по такому числу — гейт по шуму, и он же гонит на
  лишний круг ради долей балла. Критерий выхода счётный: цикл не покидается, пока
  остаётся хотя бы одна находка critical/major.

## 10. Коммит

**Вход:** пройденные ворота и ревью.
**Выход:** атомарный коммит, сразу отправленный в удалённый репозиторий.
**Готово, когда:** одна задача — один коммит; карта разработки обновлена в том же
коммите; `git push` сделан.

* Сообщение объясняет ПОЧЕМУ, с числами замера, а не перечисляет файлы.
* Никакого «заодно отрефакторил соседнее»: то, что вне контракта, не трогается.
* Запись в карту разработки — в том же коммите, держится гейтом
  ([07-КАРТА-РАЗРАБОТКИ.md]).
* **Никогда не оставлять коммиты локальными.**

---

## 11. Выкат

**Вход:** коммит в основной ветке.
**Выход:** обновлённый прод.
**Готово, когда:** скрипт выката прошёл целиком: собрать → миграции → дождаться
health → обновить карту.

Один скрипт, гарантирующий порядок, и ворота выката — [09-ВЫКАТ.md]. Никогда не
перезапуск без пересборки: он оставляет в проде старый образ при «успешном» выкате.

---

## 12. Живой смоук

**Вход:** выкаченный прод.
**Выход:** подтверждение фактами с живой системы.
**Готово, когда:** пройден весь список ниже, расхождения разобраны.

**Обязателен. Тесты его не заменяют.** Механизм, ни разу не запущенный на настоящих
данных, не работает, сколько бы зелёных тестов на него ни было.

1. Здоровье сервисов — `/health` каждого затронутого.
2. **Один настоящий прогон** от начала до конца на живых данных.
3. Фронт: реальный браузер, полностраничный скриншот, **критичный взгляд на
   вёрстку** — наложения, отступы, перенос длинных подписей, читаемость. Компонент
   может проходить все тесты и выглядеть коряво. Мобильную ширину смотреть **в
   первую очередь**, если она основная у пользователей.
4. Бэкенд: живой запрос к проду, проверка **фактом в базе — не по логу**. Лог,
   пишущий «доставлено» без проверки результата отправки, месяцами рапортует успех
   при мёртвой доставке.
5. Чтение журнала прогона: сработали ли новые механизмы (логировать каждое
   срабатывание счётчиком — «выправлено N», «спрятано M»).
6. Сравнение с предыдущим прогоном — **по списку замечаний, а не по общей оценке**.

Что живой проход ловит, когда всё остальное зелёное: блок, невидимый из-за порядка
маунта; валидатор, отбрасывающий легитимный ввод; кнопку белым по белому; круг
импортов; механизм, ни разу не сработавший; молчаливый переход на запасного
поставщика моделей.

## 13. Закрытие

**Вход:** пройденный смоук.
**Выход:** отчёт владельцу + обновлённые память, карта, передача контекста.
**Готово, когда:** все шесть пунктов сделаны и следующий шаг очереди начат.

1. Отчёт владельцу: что сделано, **чем подтверждено**, что **не проверено живым
   прогоном**, что заблокировано и чем разблокируется; человеческое объяснение, чем
   каждая находка грозит ([02-РАБОТА-С-ВЛАДЕЛЬЦЕМ.md]).
2. Работа, не проверенная владельцем вживую, получает в карте статус «ждёт живой
   проверки», а не «готово» — непроверенность должна накапливаться видимо, а не жить
   строкой в отчёте, который читают один раз.
3. Запись в память, если появилось знание, которого нет в коде ([03-ПАМЯТЬ.md]).
4. Обновление передачи контекста, если сессия была большой ([04-ПЕРЕДАЧА-КОНТЕКСТА.md]).
5. **Пересмотр карты — по своду входящих, а не по календарю задач.** Спроси
   свод (`python3 scripts/inbox-svodka.py`). Он молчит — владелец ничего не
   писал, пересматривать нечего: просто берёшь следующее по карте. Он выдал
   сортированный список — вот тогда пересмотр: перечитать его слова и
   переставить карту, если они это меняют (завести карточку, поднять приоритет,
   снять ненужное). Владелец 12.09.2026 поправил ровно это: «Тебе нужно
   пересматривать не после каждой своей задачи, а после скрипта, который
   отработал и выдал тебе сортированный список сообщений. Если я не пишу — ты
   просто работаешь по карте». Замысел он назвал раньше: «чтобы ты всегда ясно
   видел карту разработки и не сливался от моих идей и указаний». Сортировка
   весами — половина дела: она расставляет то, что уже в карте, а пересмотр
   решает, что в ней вообще должно быть.
6. Отчёт — не конец работы: следующий шаг очереди делается в том же ходе.

## Чем физически делаются «разные проходы»

Все «отдельные проходы» этой главы — ревью спеки, контракт, ловушки, автор тестов,
автор кода, ревьюеры, арбитр — делаются **субагентами: отдельными запусками агента
со своим контекстом и своей узкой задачей**. Это не риторическая фигура «свежий
взгляд», а техническая деталь, без которой схема не работает:

* **свой контекст = честный взгляд.** Автор кода, ревьюирующий свой код, видит
  замысел, а не текст. Отдельный запуск видит только текст — и находит то, что
  замысел прикрывал;
* **ревьюеры запускаются параллельно, одним заходом** — три узких прохода стоят
  почти столько же времени, сколько один;
* **исполнителю ловушек и автору тестов реализацию не показывают** — иначе они
  перескажут её вместо того, чтобы проверить требование.

Практический минимум: научись запускать проход с чужим контекстом (в текущей
оболочке — встроенный механизм субагентов) до большой работы; без этого «разные
роли — разные проходы» остаётся благим пожеланием. Какие проходы кому достаются:

| проход | кто делает | что видит | что НЕ видит |
|---|---|---|---|
| ревью спеки | сильная модель, не автор спеки | спека + кодовая база | — |
| контракт задачи | агент-аналитик | план + код | черновики реализации |
| ловушки | отдельный исполнитель | контракт + код | реализацию |
| тесты | автор тестов | контракт + зависимости | реализацию |
| код | автор кода | контракт + тесты + ловушки | право править тесты |
| ревью кода | 1–3 ревьюера параллельно | дифф + контракт | — (не автор кода) |
| сведение | арбитр / оркестратор | все находки | — |

## Специфика оболочки: навыки (skills)

В Claude Code цикл поддержан готовыми навыками публичного плагина (superpowers);
на новом проекте их можно поставить как есть. Каждому навыку нужна строка «когда» —
установленное без условия срабатывания молчит (см. [03-ПАМЯТЬ.md]):

| навык | когда |
|-------|-------|
| `brainstorming` | перед творческой работой — выяснить намерение до реализации |
| `writing-plans` | есть спека → нужен план |
| `executing-plans` | план исполняется в отдельной сессии с чекпоинтами |
| `subagent-driven-development` | план исполняется субагентами в текущей сессии |
| `test-driven-development` | перед написанием кода |
| `systematic-debugging` | любой баг — до предложения фикса |
| `requesting-code-review` / `receiving-code-review` | ревью с технической строгостью, без формального согласия |
| `verification-before-completion` | перед заявлением «готово» — доказательства до утверждений |
| `using-git-worktrees` | изоляция рабочего пространства |

## Стоп-условия

* **Отказ окружения** (упала база, очередь, хранилище секретов) — не «блокер
  задачи», а остановка: чинится окружение, задача ждёт.
* **Спека неполна** — остановка с флагом, а не додумывание.
* **Два круга ревью не сошлись** — эскалация владельцу.
* **Деградация контекста** — не «дожать любой ценой», а передача контекста и
  продолжение с точной координаты ([04-ПЕРЕДАЧА-КОНТЕКСТА.md]).
