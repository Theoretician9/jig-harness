## 1. Спека

**Вход:** запрос владельца — бриф, макет, репорт.
**Выход:** `docs/specs/<дата>-<имя>.md`.
**Готово, когда:** каждое утверждение о существующей системе проверено фактом;
статус «СОГЛАСОВАНО» от владельца.

Пишется ДО любого кода. Шаблон — `harness/шаблоны-задач/spec-template.md`. Обязательные разделы:

| раздел | содержание |
|--------|-----------|
| заголовок + источник | откуда пришло, ссылка на макет/бриф |
| статус | «итерация N — после ревью владельца», «ждёт согласования», «СОГЛАСОВАНО» |
| решения владельца | зафиксированы дословно, с датой — единственная защита от «мы же договаривались иначе» через три недели |
| §0 «Отдельно и вперёд» | найденное попутно, что чинится РАНЬШЕ основной работы (обычно обман пользователя или блокер) |
| зачем | проблема словами продукта, не кода |
| что берём / что не берём | таблица решений по каждому элементу. **«Не берём» с причиной — обязательно**, иначе заведут заново |
| целевая архитектура | что появится и как ложится на существующее |
| разделы по механикам | каждая с состояниями, крайними случаями, форматом данных |
| фазы | с оценкой и **критериями приёмки на каждую** |
| бюджет | деньги на внешние сервисы, если работа их тратит |
| проверенные факты | что проверено по коду/базе фактом, а что предположение — помечено раздельно |
| стандарты | у задачи-разработки: актуальные RFC, которые она задевает, и их ДОЛЖНО — или одна строка «стандартов нет» |
| приложение с ревью | находки adversarial-ревью + решение владельца по каждой |

**Блок «## Для человека» — ПЕРВЫЙ раздел** после шапки (до «§0»): шесть жирных
подпунктов — Суть · Как работает · Почему так · Зачем · Устройство (архитектура) ·
Что увидишь ты. Потолок тела — `ДЛЯ_ЧЕЛОВЕКА_ПОТОЛОК` (2 500 знаков, константа в
`scripts/spec_approval.py`). Простыми словами, без id задач, ярлыков, путей и имён
кода — как говорит владелец (`память/TONE.md`). Этот блок и есть текст сообщения
владельцу при `spec_approval.py --отправить`; без блока отправка — отказ.

**Язык требований — по RFC 2119 и RFC 8174 (BCP 14).** Каждое требование спеки
помечается словом силы, набранным ЗАГЛАВНЫМИ: только заглавное слово — требование,
строчное «должно» — обычная речь (это и есть уточнение RFC 8174).

| слово | RFC 2119 | смысл в спеке |
|-------|----------|---------------|
| **ДОЛЖНО** | MUST / REQUIRED / SHALL | безусловно; у каждого ДОЛЖНО — критерий приёмки или проба, которой его проверят |
| **НЕ ДОЛЖНО** | MUST NOT / SHALL NOT | безусловный запрет; проверяется так же |
| **СЛЕДУЕТ** / **НЕ СЛЕДУЕТ** | SHOULD / SHOULD NOT | так делать, если нет причины иначе; отступление записывается с причиной |
| **МОЖЕТ** | MAY / OPTIONAL | на выбор исполнителя; реализация без этого пункта не ошибочна |

Раздел «Для человека» словами силы не пишется — он для владельца, не для исполнителя.

**Раздел «## Стандарты» — у задачи-разработки обязателен.** Задача задевает протокол
или формат (HTTP, OAuth, JWT, JSON, даты и время, почта, URI, CSV, cookie, TLS…) —
автор находит АКТУАЛЬНЫЙ RFC, а не тот, что помнит: стандарты заменяются
(Obsoleted-by) и дополняются (Updated-by), и спека по заменённому документу
вшивает в код устаревшее поведение. Номер и цепочку замен даёт дешёвый инструмент
без модели — `python3 scripts/standard-current.py <номер|слова названия>` (индекс
rfc-editor.org, кэш неделю). В раздел вписываются номер, его обновления и
ключевые ДОЛЖНО стандарта, которые задача обязана соблюсти. Не задевает —
одна строка «Стандартов нет: <почему>». Без раздела `spec_approval.py --отправить`
отказывает, гейт `check-pipeline.py` ставит находку шагу «спека» задачи в работе,
`spec_approval.py --стандарты` прогоняет правило по всей карте
(судятся карточки, заведённые с 19.11.2026: старые спеки писались без него).

Отправные номера — проверить инструментом перед записью, это не замена ему:
HTTP — 9110, 9111, 9112 · cookie — 6265 · OAuth 2.0 — 6749 и его обновления ·
JWT — 7519 · JSON — 8259 · даты и время — 3339 · почта — 5322 · URI — 3986 ·
CSV — 4180 · TLS 1.3 — по инструменту (8446 заменён).

Два правила, спасавшие чаще всего:

* **любое утверждение о существующих данных проверять фактом** — запросом к базе,
  чтением кода. Спека, называющая неверную причину бага, ведёт реализацию чинить не то;
* **критерий приёмки — проверяемый предикат.** Не «страница выглядит хорошо», а
  «замер даёт ноль замечаний, проверка доступности — ноль serious».
