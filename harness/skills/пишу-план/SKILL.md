## 3. План реализации

**Вход:** согласованная спека.
**Выход:** `docs/plans/<дата>-<имя-или-фаза>.md` — по документу на фазу.
**Готово, когда:** каждая задача имеет файлы с путями, интерфейсы, шаги с чекбоксами
и требования к тестам; общие ограничения собраны в шапке.

Шаблон — `harness/шаблоны-задач/plan-template.md`. План — не пересказ спеки, а последовательность
задач для исполнителя:

* **Шапка — общие ограничения**, которые исполнитель обязан знать до первой строки:
  где живёт логика; какие поля НЕ вводить (потому что уже есть); что не трогать;
  как гонять тесты (если набор нестабилен поимённо — сравнивать только полным
  прогоном); чего нет в окружении; язык комментариев; какой трейлер несёт коммит.
* В шапке же — сквозные требования: **тест до кода** и **замер на живом обязателен
  помимо теста** (есть случаи, где зелёные тесты закрепляли неверное допущение).
* Задачи `Task 0..N`, каждая: ссылка на раздел спеки; список файлов
  (изменить/создать) **с абсолютными путями и номерами строк**; интерфейсы (что
  принимает, что отдаёт); шаги с чекбоксами `- [ ]` — план заодно служит трекером;
  **требование к тесту** — что он проверяет и почему (см. шаг 6).

## Процессные: порядок действий создаёт беду

**Выкат убивает работу — и наоборот.**
Симптом: долгая задача исчезает, в базе висит вечное «выполняется». Механизм:
пуш → авто-выкат → перезапуск воркеров; идущая задача без повтора умирает.
Обратный случай: выкат, начатый ДО запуска задачи, доедет во время неё.
Защита: сторож перед выкатом И перед запуском долгой задачи; сверка кода в
контейнере с рабочим деревом; брошенные задачи закрываются фоновой уборкой —
`scripts/deploy_guard.py`, [09-ВЫКАТ.md].

**Пустая переменная в shell = «всё».**
Симптом: команда, адресованная одному сервису, накрывает весь стек. Механизм:
`docker compose up -d $СПИСОК` при несозданной переменной разворачивается в
команду без аргументов — то есть «все сервисы». Защита: перед опасной командой
проверять, что переменная непуста (`${СПИСОК:?}`); `set -u` в каждом скрипте.

**Кириллица в разовых командах оболочки.**
Симптом: правило «имена переменных только латиницей» записано — и нарушается
именно в однострочниках и циклах «на один раз» (`for p in ...; do имя=$(...)`),
не в скриптах. Механизм: условие правила было «пишу скрипт», а нарушение живёт
в разовых командах — правило молчит там, где срабатывает беда. Защита: условие
правила — «набираю `=` после слова в любой строке для оболочки»; разовую
обработку писать не на bash, а `python3 - <<'PY'` — там кириллица законна и
соблазна нет.

**Команда из плана, которой не существует.**
Симптом: исполнение плана спотыкается на шаге, который невозможно выполнить
(команды нет в образе, путь не существует). Механизм: план писался по аналогии
с другим проектом, а не по устройству этого; план — тоже утверждение, и оно
тоже требует улики. Защита: команды плана проверяются ДО того, как на них
опираются, — один прогон каждой на пустом/безопасном входе на этапе ревью
плана — [05-ПАЙПЛАЙН.md].

**Одно знание в двух местах.**
Симптом: дефект «починен», но болит ещё сутки; два порога с комментарием
«число то же» расходятся. Механизм: продублированная константа или ветка логики
правится в одном месте из двух — копии никто не ищет, потому что о них не
помнит. Защита: одна константа, импортируемая всеми потребителями; при починке
искать вторую копию поиском по коду, а не по памяти.

**Правка, замеренная на одном примере.**
Симптом: «исправлено» ломается на втором объекте. Механизм: частный случай
принят за общий — один пример не отличает закономерность от совпадения.
Защита: прогон минимум на трёх непохожих объектах до вывода —
[06-ГЕЙТЫ-КАЧЕСТВА.md], [08-ПРИБОРЫ-И-ЗАМЕРЫ.md].

**Разделяемая среда у параллельных прогонов.**
Симптом: десятки несвязанных падений тестов, странные 401/429, прогон умирает
на середине. Механизм: два прогона бьют в одну тестовую базу и стирают
фикстуры друг друга; тесты в боевом контейнере пачкают боевые метрики; полный
прогон параллельно с выкатом умирает вместе с контейнером. Защита: каждому
прогону — своя база (шаблон + создание по идентификатору воркера); при
массовых странных падениях СНАЧАЛА искать второй прогон, потом дебажить код;
тесты не запускаются параллельно с коммит-гейтом и выкатом —
[06-ГЕЙТЫ-КАЧЕСТВА.md].

**Параллельный стейджинг при идущем коммите.**
Симптом: в коммит попали чужие файлы. Механизм: `git add` во время чужого
`git commit` с долгим хуком — git фиксирует индекс в момент финализации, после
хука. Защита: один юнит работы = один полный цикл add+commit+гейт; агентов
можно параллелить, коммитить — по очереди.

**Многострочные сообщения и трейлеры git.**
Симптом: машиночитаемые трейлеры коммита не распознаются; сообщение схлопнулось
в одну строку. Механизм: трейлеры работают только единым блоком без пустой
строки между ними; многострочный `-m` ненадёжен. Защита: сообщение передавать
через `git commit -F -`, трейлеры держать одним блоком —
[07-КАРТА-РАЗРАБОТКИ.md].

**Конфиг, который монтируется фрагментом, а не целым файлом.**
Симптом: после `docker cp конфиг <контейнер>:/etc/.../главный.conf` проверка
конфигурации краснеет, перечитывание не проходит; сервис работает на прежней
настройке, а конфиг в контейнере испорчен. Механизм: репозиторный файл
монтируется в каталог включений **фрагментом** (`conf.d/`), а главный конфиг
принадлежит образу — копирование поверх главного затирает то, что файлу не
принадлежало. Защита: перед копированием смотреть, **куда именно** файл
смонтирован (`volumes:` в описании сервиса); главный конфиг восстанавливается
из образа: `docker run --rm <образ> cat <путь>`.

**Дрейф конфига на хосте.**
Симптом: баг ищут в коде, которого на проде нет; правки «не действуют».
Механизм: живой конфиг (прокси, демоны) правился руками мимо репозитория и
разошёлся с источником истины. Защита: источник истины — репозиторий; после
любой правки — дифф с живым конфигом; проверка всех маршрутов скриптом —
[10-СЕРВЕР-И-НАДЁЖНОСТЬ.md].

**Файлы мимо конвейера доставки.**
Симптом: страница частично сломана; прод содержит то, чего нет в истории, и
следующий выкат это затирает. Механизм: копирование собранного из staging в
прод или `docker cp` в работающий контейнер обходит единственный законный путь
доставки. Защита: прод обновляется только слиянием и сборкой; правка в живом
контейнере — костыль для итерации, перед проверкой и отчётом — полный выкат —
[09-ВЫКАТ.md].

**Кеш апстрима у обратного прокси.**
Симптом: после выката «ничего не изменилось». Механизм: прокси держит старый
адрес пересозданного контейнера, трафик идёт в никуда. Защита: перечитать
конфигурацию прокси ПРЕЖДЕ, чем искать дефект в коде — [09-ВЫКАТ.md].

**Фоновый агент занимает ресурс живого сеанса.**
Симптом: канал связи с владельцем обрывается в момент запуска фонового скрипта
или «безобидной» диагностики. Механизм: некоторые ресурсы допускают ровно
одного потребителя (например, канал доставки сообщений на один токен), и новый
держатель убивает старого — то есть живой рабочий сеанс. Защита: фоновые
запуски — с пустой конфигурацией расширений; состав расширений смотреть чтением
конфигов, а не health-check-командами; проверить единственность потребителя для
СВОЕГО канала до постановки крона — [13-УСТРОЙСТВО-И-КОНФИГУРАЦИЯ.md],
[02-РАБОТА-С-ВЛАДЕЛЬЦЕМ.md].

**Одноразовые состояния на клиенте.**
Симптом: после сброса аккаунта на сервере пользователь не видит приветствий и
туров; удалённые данные «воскресают». Механизм: одноразовость гейтится по
браузерному хранилищу, которое сервер не сбрасывает; черновик из браузера
переотправляется в чистый профиль. Защита: одноразовые впечатления гейтить по
серверному состоянию; живой проход после сброса — только в приватном окне.
