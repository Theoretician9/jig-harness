# 03 — ЗАДАНИЕ НОВОМУ АГЕНТУ: первые сессии

> Ты — Claude Code на этом сервере. Этот документ ты читаешь первым; он
> отвечает на четыре вопроса: что читать, что настроить, что сделать первым,
> как отчитаться. Другие источники, кроме файлов этого пакета и разложенного
> харнеса, не нужны.

## 0. С первой минуты — правила общения

Действуют ДО того, как ты дочитаешь остальное:

1. Владелец — в Telegram, терминал он не видит. Всё значимое — в канал
   (`scripts/tg_send.sh`), файлы вложением.
2. **Ack ≤ 30 секунд** на любое входящее: «принял, делаю X» — потом работа.
   Входящие владельца диспетчер складывает файлами в `$LOG_DIR/inbox/` — это
   твоя очередь: проверяй её в начале хода и на рубежах, прочитанное переноси
   в `inbox/обработано/` (напомнит session-warden, но его пинок значит, что
   сообщение уже ждало).
3. **Анонсировал — продолжай.** Никаких интерактивных вопросов и ожиданий в
   терминале; вопрос владельцу — сообщением с нумерованными опциями, и если
   работа может идти — она идёт.
4. Режим — **полуавтомат**: выкат, ротация, необратимые операции — только
   после анонса и подтверждения владельца (диспетчер складывает ответы в
   `$LOG_DIR/confirmations.jsonl`). Остальное — сам, без спроса.
5. Честность отчёта (И-4): непроверенное живым прогоном называется «ждёт
   твоей проверки», не «готово».

## 1. Что читать (строго в этом порядке)

1. `CLAUDE.md` — правила, инварианты И-1…И-4, команды (5 минут).
2. `STATE.md` + `память/MEMORY.md` (таблица срабатываний) — грузятся сами.
3. Главы UNIFIED (каталог `UNIFIED/` доставлен раскладчиком; если его нет —
   скажи владельцу, скилы работают и без него) — по норме `UNIFIED/00`:
   **02 → 01 → 03 → 04 → 05 → 13**
   (работа с владельцем — первой: несостыковки в общении дороже технических
   ошибок). Остальные главы — по мере надобности; полные процедуры шагов
   придут скилами (`skills/`) по условию срабатывания.
4. `harness/ОПИСЬ.md` — что за механизмы вокруг тебя и чем каждый проверяется.

## 2. Что настроить (чек-лист готовности, глава 14-А)

Установка по `01-SPEC-УСТАНОВКА.md` уже выполнена человеком/агентом до тебя
(шаги 0–7). Твоя часть — довершить и ДОКАЗАТЬ (это задачи `hr.accept` в
dev-map):

- [ ] `git init` в каталоге проекта (если ещё нет) → повторить
      `razlozhit-harnes.sh` (подключит pre-commit симлинком) → первый коммит
      каркаса.
- [ ] Шаги 8–9 установки: crontab демонов, прогон каждого `env -i` (образец в
      01-SPEC §9).
- [ ] Каждая проверка — на заведомо больном случае (список — `ОПИСЬ.md`,
      раздел «Доказывается на живом»): сторож отменяет запрещённую команду;
      `check-secrets` краснеет на подложенном токене; закомментированный демон
      назван в утренней сводке; бэкап восстановим на чистом каталоге.
- [ ] Канал доказан фактом: сообщение дошло (владелец ответил), ack ≤30 с.
- [ ] Числа потолков `harness.conf` сверены с фактическим тарифом VPS.
- [ ] Отчёт владельцу по `ЧЕК-ЛИСТ-ПРИЁМКИ.md`: каждый пункт — команда и её
      вывод, не слова.

## 3. Дисциплина рубежей и первая ротация (обязательно)

Правило: **компакт — сигнал, а не норма; больше одного компакта подряд
запрещено — дальше ротация.** Чтобы ротация была бесшовной в любой точке:

* обновляй `docs/handover/SESSION-HANDOFF-<дата>.md` **на каждом рубеже шага
  пайплайна** (закрыл спеку — обновил; закончил тесты — обновил), а не когда
  окно уже забито. За протухшей передачей следят `stop_reminder.sh`,
  `pre_compact.sh` и session-warden — но их напоминание значит, что ты уже
  опоздал;
* по команде надзирателя (session-warden): закончи текущий атомарный шаг —
  шаг не рвётся посреди правки, — финализируй передачу, заверши сессию штатно.

**Первая ротация прогоняется принудительно** (задача `hr.rotation`), до
первой задачи продукта: попроси владельца подтвердить, заполни передачу,
заверши сессию; новая сессия обязана назвать текущую задачу и следующий шаг
без наводящих вопросов. Расхождение — дефект передачи: чини шаблон передачи,
не память. Результат (бесшовно / что потерялось) — в отчёт и в
`$LOG_DIR/rotation.jsonl`.

## 4. Первая задача продукта — проверка харнеса (задача `pr.first`)

Возьми первую реальную задачу владельца — маленькую — и прогони через **весь**
цикл: спека → ревью спеки → план → pretask → тесты до кода → код → ворота →
ревью → выкат → живой смоук → отчёт → память → карта. Скилы ведут по шагам;
каждый вызов скила пишется в журнал (первая строка каждого SKILL.md).

Перевод задачи в `done` — только после подтверждения владельца: поле
`tested_at` в dev-map (гейт И-4 в pre-commit не пустит `done` без него;
внутреннее — `owner_testable: false`).

Цель — не задача, а обнаружение мест, где цикл рвётся. **Рвётся обязательно.**
Каждый разрыв: запись в `память/` (что случилось, дата) + предложение
механизма-страховки по лестнице носителей (демон → хук → скрипт → скил →
контекст) — голое «буду помнить» не считается носителем. Закрытие задачи
дополняет разделы «Домен»/«Архитектура» в CLAUDE.md.

## 4-а. Крупные наборы — по условию, не заранее

Расширения ставятся строкой таблицы (скил `установка-расширений`). Наборы
крупнее — «возможности»: каталоги с паспортом в `harness/vozmozhnosti/`. Пока
набор не установлен, его скилов НЕ существует, его запреты сторож не читает,
его каталоги уборщик не чистит — контекст и сервер чисты.

```bash
bash scripts/vozmozhnost.sh список                # что есть и при каком условии
bash scripts/vozmozhnost.sh требования <id>       # замер ДО установки, с адресом у каждого «нет»
bash scripts/vozmozhnost.sh поставить  <id>
```

В комплекте один набор — `мобильная-разработка` (React Native + Expo, Android
на этом сервере, iOS через EAS). Условие включения: **в задаче продукта
появилось мобильное или клиентское приложение**. Наступило — анонсируй в канал,
поставь, и СРАЗУ отправь владельцу вложением
`docs/возможности/мобильная-разработка-РУКАМИ.md`: там браузерные шаги, оплаты и
проверки на живом устройстве, которые из сессии физически не сделать. Приёмка
набора — его собственный `ЧЕК-ЛИСТ.md`; до неё работа с приложением носит статус
`test`.

Раньше условия не ставить: набор просит ~20 ГБ диска и держит эмулятор в
памяти рядом с тобой.

## 5. Свои улики — с первого дня (глава 14-Б)

Правило без ТВОЕГО случая — чужая мудрость, её отменяют первой. С первого
дня: каждая поправка владельца — запись с датой и дословной цитатой; каждый
дефект — «какое правило не дало бы повториться»; спроси владельца одной
строкой: «какие у тебя есть правила про то, как я должен работать и писать
код?» — запиши дословно с датой. Скил `добыча-улик` ведёт по методике.

## 6. Как отчитаться (по каждому блоку выше)

Отчёт в канал: что сделано → чем доказано (команда + вывод/число) → что «ждёт
твоей проверки» → следующий шаг. Приёмка харнеса целиком — по
`ЧЕК-ЛИСТ-ПРИЁМКИ.md`; после неё владелец решает переход semi → full
(строка `AUTONOMY` в install.conf — меняет её только он).
