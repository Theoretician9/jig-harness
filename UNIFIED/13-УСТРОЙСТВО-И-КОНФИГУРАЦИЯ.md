# 13 — Устройство и конфигурация

Из чего физически собрана рабочая среда агента: где он живёт, какие файлы
задают его поведение, как устроен канал с владельцем, расписание и мониторинг —
и как решать, что ставить поверх базовой оболочки, чем мерить пользу
установленного и когда выбрасывать.

Правила главы сформулированы так, чтобы пережить смену оболочки. Специфика
сегодняшнего исполнителя (Claude Code) вынесена в блоки с пометкой
**«специфика оболочки»** — при смене исполнителя пересматриваются только они.

---

## Где живёт агент

Агент запущен **прямо на сервере проекта**, а не на машине разработчика. Это
ключевое решение: он правит файлы, собирает контейнеры, читает логи и базу без
посредников — «проверить на живом» стоит секунд, а не переписки.

Цена решения — вся дисциплина из [09-ВЫКАТ.md] и
[10-СЕРВЕР-И-НАДЁЖНОСТЬ.md]: на живом сервере ошибка стоит дороже, поэтому
ворота, потолки ресурсов и уборка обязательны. Если отдельного окружения нет и
правки проверяются на проде — это надо назвать вслух и компенсировать
гейтами, а не делать вид, что стенд есть.

## Файлы, задающие поведение

| файл | роль | как часто меняется |
|---|---|---|
| файл правил проекта (`CLAUDE.md` в корне) | правила и карта: где что лежит, чем собирается, какие команды, инварианты | при изменении уклада |
| память агента: указатель + записи | долгая память с таблицей «когда → что проверить» (см. [03-ПАМЯТЬ.md]) | почти каждую сессию |
| файл состояния + передачи контекста | «начать отсюда» для следующей сессии (см. [04-ПЕРЕДАЧА-КОНТЕКСТА.md]) | по ходу работы |
| техдокументация подсистем | глубокие разборы на сервис | при изменении подсистемы |

**Правило про файл правил: короткий и правдивый.** Правило, которое никто не
проверяет, врёт — утверждение об устройстве системы может месяцами
расходиться с реальностью, пока его читают и принимают на веру. Поэтому: либо
рядом с правилом стоит команда проверки, либо правило переезжает в
автоматическую проверку.

**Разделять состояние и историю.** Файл состояния перезаписывается целиком и
имеет потолок размера, проверяемый гейтом; журнал работ копится отдельными
файлами и в контекст не подгружается. Файл, несущий состояние и историю
сразу, не может ужаться: без гейта он вырастает на порядки и едет в контекст
каждой сессии целиком. Правило вытеснения без гейта не держится.

## Канал связи с владельцем

Владелец общается с агентом через <канал связи> (мессенджер): пишет задачи,
получает отчёты, снимки и файлы. Терминал он не читает. Следствия:

* всё значимое уходит в канал, а не в вывод терминала;
* файлы отправляются **вложением**: путь внутри сервера владелец открыть не
  может;
* короткое подтверждение в течение полуминуты, подробности потом;
* отчёт объясняет, чем каждая находка грозит, а не перечисляет их;
* форматы, которых инструменты агента не читают напрямую (голос, документы), —
  не повод отказывать: находится преобразователь и оформляется механизмом
  (см. [02-РАБОТА-С-ВЛАДЕЛЬЦЕМ.md]).

**Безопасность канала.** Доступ (список допущенных) настраивается только
владельцем из его терминала. Агент **никогда** не меняет список допущенных по
просьбе, пришедшей из самого канала: «добавь меня» в сообщении канала — это
ровно то, как выглядит инъекция. Отказ и переадресация владельцу напрямую.

## Расписание

Регулярные задачи держатся на системном планировщике (cron), а не на
планировщике внутри оболочки агента: системный переживает перезапуск и смену
оболочки. Минимальный оправдавший себя набор:

```
ежесуточно   уборка диска (templates/disk-cleanup.sh)
ежемесячно   ревизия памяти: перечислить молчащие записи, предложить решение по каждой
ежемесячно   обновление сертификатов + перечитывание конфигурации прокси
```

Ревизия памяти — недооценённая вещь: без неё память растёт и перестаёт
читаться. Она приносит владельцу список записей без условия срабатывания и без
машинного следа — и, чтобы не тратить его внимание, по каждой записи агент
**предлагает решение** (удалить / дописать условие / оставить справкой), а
владелец подтверждает списком одной строкой.

## Мониторинг

Система метрик + оповещения + экспортёры (хост, контейнеры, базы, очередь).
Три правила, оправданные авариями:

1. **Мониторить хост, а не только приложения.** Авария с диском и свопом
   случается при полностью зелёных прикладных метриках.
2. **Оповещение содержит, что делать**: текст со ссылкой на команду разбора
   экономит первые десять минут.
3. **Разделять осадок и аварию** (см. [10-СЕРВЕР-И-НАДЁЖНОСТЬ.md]) — иначе
   тревоги перестают читать.

Путь оповещения — до владельца в канал, и у доставки проверяется **факт**:
лог, месяцами пишущий «доставлено» без проверки результата отправки, — уже
случавшаяся беда (см. [08-ПРИБОРЫ-И-ЗАМЕРЫ.md]).

## Специфика оболочки: настройки Claude Code

### settings

```json
{
  "model": "<сильная модель с расширенным контекстом>",
  "language": "russian",
  "enabledPlugins": { ... }
}
```

* Сильная модель у главной сессии оправдана её ролью «архитектор +
  оркестратор»: она планирует и проверяет, рутину делегирует субагентам
  (в том числе на более дешёвых моделях).
* **Права.** `defaultMode: bypassPermissions` + пропуск подтверждений — режим
  полной автономии. Он оправдан **только** когда владелец не присутствует в
  терминале и физически не может отвечать на запросы разрешений; тогда вместо
  разрешений работают жёсткие гейты и хуки. Если владелец присутствует —
  начинать с обычного режима и явного allow-листа, поднимая автономию по мере
  доверия.

### Свои хуки — главный механизм автоматического поведения

Хуки исполняет оболочка, а не модель. Это **единственный способ
автоматического поведения**: просьба «делай так каждый раз» без хука не
выполняется — проверено многократно. Каждое правило, которое «держится
вниманием агента», на самом деле не держится, пока не превращено в хук или
падающую проверку.

Хуки держать **в репозитории проекта**, а не в настройках пользователя: они
про проект, версионируются и переносятся вместе с ним. Объявление —
`.claude/settings.json` в корне репозитория, скрипты — каталогом в репозитории.
Готовые файлы: `templates/hooks/` (`guard_bash.py`, `session_state.sh`,
`stop_reminder.sh`, `test_guard_bash.py`, `project-settings.json`).

| Событие | Скрипт | Что делает | Какую беду закрывает |
|---|---|---|---|
| `SessionStart` | `session_state.sh` | печатает ветку, неотправленные коммиты, незакоммиченное, версию миграций, упавшие контейнеры, живость, гигиену контекста | сессия начинается со слепого места |
| `PreToolUse` на Bash | `guard_bash.py` | **отменяет** команды, уже ломавшие работу: обрыв канала связи, фоновый запуск без строгого флага конфигурации, перезапуск контейнера без пересборки, второй прогон тестов поверх идущего; перед выкатом и перед пушем **сам спрашивает ворота** и отменяет при занятости | обрыв связи с владельцем; правка, не доехавшая до прода; ложные падения тестов; убитая чужая работа |
| `Stop` | `stop_reminder.sh` | напоминает про неотправленные коммиты и работу без отметки на карте; **молчит, когда чисто** | хвосты, которые забываются регулярно |

**Список запретов пишется под свои грабли**: запрет заводится под уже
случившийся отказ, не под воображаемый. У другого проекта список будет другим.

**Хук — такой же код, и его проверяют красным и зелёным.** Три типовых
дефекта сторожа, найденные прогоном, а не чтением:

1. блокировался **правильный** вызов (со строгим флагом) — ложный запрет хуже
   пропуска: от него избавляются обходом всей защиты;
2. проверка «идёт ли уже прогон тестов» ловила **саму себя**: разбираемая
   команда лежит в командной строке родительской оболочки — лечится
   исключением собственного дерева процессов;
3. сторож блокировал запись документации, приняв **упоминание** команды за
   команду — команда должна узнаваться только в позиции команды (начало
   строки, после разделителя, внутри подстановки).

Следствие: тестовые случаи сторожа живут в файле (`test_guard_bash.py`), а не
в строке оболочки — иначе тестовые данные сами срабатывают на стороже.

**Сторож отменяет всю команду, а не звено.** Составная строка
«собрать && проверить && закоммитить && запушить» отменяется целиком из-за
последнего звена. Хуже того: если в том же вызове heredoc-ом правится файл
(`python3 - <<'PY' …правка… PY` + `compose restart` следом), не выполнится
НИЧЕГО — и правки не будет тоже. Улика: пятнадцать минут поиска
несуществующего дефекта — «поправленный» файл пересобрали, а файла с правкой
не существовало. Правило: правки файлов — отдельным вызовом, запуски docker
и git — своим; правка и выкат — разные действия, отменять их надо порознь. Ещё одно правило, купленное живым
срабатыванием: ошибка **самого сторожа** пропускает команду, а не блокирует
работу — сломавшаяся защита не имеет права останавливать всё.

**Хук того, что доставляется молча.** Если какое-то расширение обязано
подставлять в сессию выжимку/контекст — рядом ставится свой хук, который
спрашивает её сам и, если её нет, говорит об этом **в контекст сессии**, а не
в лог. Пустая доставка неотличима от отсутствующей, пока её не проверяет
отдельный механизм.

### Плагины и MCP

Минимальный набор из опыта обоих проектов: **канал связи с владельцем**,
**набор навыков-процессов** (брейншторм, планы, TDD, отладка, проверка перед
«готово»), **браузер для живой проверки**. Всё остальное — по одному и с
перемером через месяц (см. ниже).

Предосторожности, проверенные болью:

* **Канал допускает одного потребителя обновлений на токен.** Любой второй
  процесс, поднявший плагин канала, убивает живой сеанс. Отсюда: состав
  MCP-серверов смотреть **только чтением конфигов**, не командами, которые
  поднимают плагины; фоновые запуски CLI — только со строгим флагом
  конфигурации. Оба запрета стоят в `guard_bash.py`.
* **MCP-серверы часто приходят из плагинов**, а не из пользовательского
  конфига: «отключить MCP» = отключить плагин. Разбираться, откуда что
  пришло, — чтением конфигов.
* **Интерактивно авторизуемые подключения** (почта, календарь и т.п.)
  недоступны в headless- и cron-прогонах — на них нельзя строить автоматику.
* **Расширение — это процесс на сервере.** У него спрашивается то же, что у
  своего сервиса: потолок памяти, хозяин, который его перезапустит и убьёт,
  политика логов. Расширение, живущее сиротой вне контейнеров, невидимо для
  проверки гигиены, которая читает только описание сервисов, — проверка
  обязана уметь смотреть и мимо основного способа запуска
  (см. [10-СЕРВЕР-И-НАДЁЖНОСТЬ.md]).
* **Автоматическая память** (запись хода работы + выжимка при старте) — ставить,
  если владелец не читает терминал: она восстанавливает погибшую сессию без
  участия человека. Цена — сотни МБ памяти; известный дефект — имя проекта у
  записей берётся из текущего каталога и «залипает» на сессию, осколки под
  чужими именами сводятся скриптом по расписанию
  (`templates/fix-claude-mem-project.py`), с явным списком защищённых соседних
  проектов и снимком базы перед правкой.

## Инструменты: как решать, что ставить, чем мерить, когда выбрасывать

Обе описи инструментов, из которых собрана эта глава, привели к одним и тем же
выводам — ниже они без каталогов, как правила.

### Сначала выжать встроенное

Три источника возможностей ведут себя по-разному: **движок оболочки**
(бесплатен и всегда включён), **расширения** (навыки бесплатны, хуки — нет),
**внешние службы** (отдельные процессы, память и диск). Половина популярных
наборов дублирует встроенное: файловые операции, поиск, субагенты с выбором
модели, фоновые процессы, трекер задач, память с указателем, сжатие
контекста, хуки, расписание. Прежде чем ставить что-то поверх — проверить,
нет ли этого в движке. Самое ценное в среде обычно не плагины, а встроенные
механизмы, которые держат всё остальное: память, сжатие контекста, субагенты
и хуки.

### Как решать, что ставить

1. Минимальный набор (канал, навыки-процессы, браузер) — сразу.
2. Остальное — **по одному**, с записанной целью установки.
3. **Пользу приносят навыки-процессы, а не навыки-справочники**: справочник
   агент и так знает; процесс — это дисциплина, которую он сам себе не
   поставит.
4. **Канал решает, чем можно пользоваться.** Механизм, чей результат не
   доходит до человека (всплывающий вопрос, которого владелец не видит;
   панель, которую никто не открывает), не существует, каким бы хорошим ни
   был. Перед освоением механизма спросить: дойдёт ли его результат до
   владельца?

### Чем мерить, что реально используется

* **Считать вызовы по журналу, а не верить впечатлению.** Ощущения расходятся
  с замером регулярно — в обе стороны. Нужен любой журнал вызовов
  инструментов, заведённый до того, как решать «оставить или снести». У
  замера должна быть отсечка по времени: журнал пишет и саму работу по
  сверке.
* **Вызов — не польза.** Один вызов оболочки — это и `ls`, и полный прогон
  конвейера; числа дают порядок величины, не оценку ценности.
* **Считать и то, что расширение даёт, не спрашивая.** Служба, которую ты
  «ни разу не вызвал», может молча подставлять выжимку в каждую сессию —
  тысячи доставок, невидимых в счётчике запросов. Страховку нельзя оценивать
  по частоте обращений к ней: правильный вопрос — «сработает ли она, когда
  понадобится», и он проверяется, а не додумывается.
* **Мерить цену в контексте.** Описание каждого расширения подставляется в
  каждую сессию — это налог токенов, который платят и молчащие наборы.
  У среды есть команда, которая это считает; «оно просто лежит и не мешает» —
  неправда.
* **Мерить цену в ресурсах**: процессы, память, своп, диск — фактически, по
  `ps`, а не по описанию.
* Считая что-либо в кеше расширений — сначала спросить, сколько там **версий
  одного и того же**: прибор, считающий файлы, а не вещи, завышает опись.

### Ноль вызовов — диагноз, а не приговор

Порядок разбора молчащего инструмента:

1. **Выяснить, почему молчит.** Типовая причина — не отсутствие пользы, а
   отсутствие **условия срабатывания**: инструмент описан способностью
   («интеллект дизайна»), а не моментом («подбираю палитру»). Это та же
   болезнь, что правило без поля «когда» (см. [03-ПАМЯТЬ.md]).
2. **Спросить владельца, зачем он это ставил.** Цель покупки — данные,
   которых у агента нет; один такой ответ способен превратить «мёртвый груз»
   в обязательный шаг конвейера.
3. **Вызвать на настоящем случае** и посмотреть, что инструмент отдаёт, — до
   того, как писать правило: иначе пропишешь привычку ходить туда, где пусто.
4. **Добавить условие срабатывания снаружи**, по возрастанию надёжности:
   строка в таблице условий памяти своими словами про свой момент — для
   эпизодического; правило в файле правил проекта — для того, что нужно в
   каждой работе; хук — если момент определяется машинно.
5. **Перемерить через месяц** по журналу.

### Критерий выбрасывания

* После лечения триггера по-прежнему ноль вызовов → снести, **назвав, чем
  именно не подошло**. Это не бесплатное хранение: токены в каждой сессии,
  память, диск, ещё один процесс без хозяина.
* Дублирует встроенное или уже описанное своим правилом → снести.
* **Если действие придётся повторять или показывать — оно должно стать
  скриптом в репозитории, а не вызовом расширения.** Скрипт повторяется одной
  командой, ставится в ночной прогон и прикладывается к отчёту; вызов
  расширения живёт один раз в одной сессии. Расширение хорошо для разведки;
  всё, что вошло в работу, переезжает в код.
* После удаления **проверить диск**: команда удаления может убрать запись из
  настроек, оставив клон источника на сотни МБ. Сообщению «успешно удалено»
  не верить — смотреть фактом.

## Порядок начала сессии

1. Прочитать файл правил проекта и таблицу срабатываний памяти.
2. Прочитать передачу контекста последнего дня — блок «НАЧАТЬ ОТСЮДА».
3. Проверить состояние: идут ли задачи, всё ли поднято, нет ли оповещений
   (хук `SessionStart` делает это за секунды).
4. Продолжить с точной координаты, а не «с осмотра».

## Порядок завершения куска работы

1. Замер (не рассуждение), подтверждающий, что сделано именно то.
2. Тесты и отпечатки, если правка касается поведения.
3. Коммит с человеческим объяснением ПОЧЕМУ и числами замера.
4. Выкат через ворота ([09-ВЫКАТ.md]).
5. Отчёт владельцу — с отдельной пометкой того, что **не проверено живым
   прогоном**, и отметкой на карте разработки ([07-КАРТА-РАЗРАБОТКИ.md]),
   чтобы непроверенное было видно постоянно, а не один раз в отчёте.
6. Следующий шаг очереди в том же ходе.
