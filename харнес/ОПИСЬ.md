## Ревизия 11.08.2026 (вечер) — улика живой установки на шаге 4

Установка на чистом VPS встала на шаге 4: systemd отбил юнит `harness-agent`
словами «has a bad unit file setting». Причина в юните была видна глазом —
`WorkingDirectory=СТАРТОВ${PROJECT_DIR}`, относительный путь с
обрубком «СТАРТОВ» впереди (склеенная вставка в терминал на вопрос 2/6).

Дорогое здесь не то, что ответ пришёл кривым, а то, что **три проверки подряд
позеленели на кривом значении**: `mkdir -p` создал каталог относительно
текущего, `chown -R` прошёл, проверка шага 1 «каталоги принадлежат агенту»
сверила владельца из того же рабочего каталога. Каждая спрашивала ФАКТ
(каталог есть, владелец тот) вместо СВОЙСТВА (путь абсолютный).

| правка | носитель | доказательство |
|---|---|---|
| ответ-путь проверяется при вводе, вопрос повторяется с примером и причиной отказа | `спросить_путь` / `путь_годен` в УСТАНОВИТЬ.sh | `--selftest`: 8 больных случаев (относительный, пустой, `/`, пробел, `..`, `$`, `;`) + 4 здоровых |
| значение проверяется ПОВТОРНО при каждом запуске до первого шага — при `--resume` вопросов нет вовсе, а конфиг мог быть поправлен руками | `сверить_пути_конфига` перед `шаг_0` | больной случай: кривой `PROJECT_DIR` + `--resume` → СТОП «ни один шаг не начинался» с причиной |
| проверка шага 0 переписана со «непусто» на «все пути абсолютны» | `проверка` в `шаг_0` | тот же прогон |
| чужой компонент выверяется ДО включения | `проверить_юнит` (`systemd-analyze verify`) перед `enable --now` обоих юнитов | видно в `--dry-run`; на машине без `systemd-analyze` — пропуск С АДРЕСОМ |
| правило вынесено из скрипта в норму | UNIFIED/11: ловушки «Проверка смотрит на факт, а не на свойство» и «Ответ человека доезжает до кода неразобранным» | глава 11 — 42 ловушки в 5 классах; скил `падение-тестов` перегенерирован и несёт новую ловушку |

Класс закрыт не заплаткой в шаге 4: значение проверяется там, где входит в
программу, и ещё раз на каждом запуске — то есть беда не может повториться ни
через другой вопрос, ни через правку конфига руками.

### Вторая находка того же вечера: «агент жив» никем не проверялось

Вопрос владельца по инструкции («мне же надо, чтобы агент работал через tmux —
или он будет работать?») вскрыл дырку, которую не показал ни один прогон.

Пункт «а» инструкции запускал `claude` ВНЕ tmux — `bash -c 'cd ~ && claude'`.
Для OAuth этого достаточно (вход сохраняется в `~/.claude/`), но рабочая сессия
там умирает с терминалом, и владельцу это нигде не объяснялось; вдобавок
рабочий `claude` предлагалось запустить потом второй раз — и командой БЕЗ
`--dangerously-skip-permissions`, то есть не той, которой сторож поднимает
агента после ротации (`AGENT_START_CMD`). Расхождение вылезло бы только после
первой ротации.

Дороже другое: **выход из Claude Code никем не сторожился**. Юнит остаётся
`active` (он держит tmux, а не `claude`), heartbeat-метки свежие, утренняя
сводка зелёная — а работать некому. Замечалось это ТОЛЬКО когда что-то
требовалось доставить: непустой inbox или непустая очередь. «Агент мёртв» —
самостоятельное состояние, и своего сторожа у него не было.

| правка | носитель | доказательство |
|---|---|---|
| «агент выпал в оболочку» — отдельная проверка каждые 10 минут: подъём тем же `AGENT_START_CMD`, сигнал владельцу с кулдауном | `session-warden.sh` §6б + чистая функция `решение_по_панели` | `--selftest` 8 путей: жив (claude/node) · владелец приаттачен → не вмешиваться · рано (порог) · первый раз увидели → засечь · брошена → поднять · редактор в панели · порог уважения выключен конфигом |
| сторож не мешает владельцу, ПОКА тот работает в панели: уважение снимается простоем | `AGENT_DEAD_RESPECT_ATTACHED` + `tmux list-clients` + `#{session_activity}` | тот же селфтест: больной случай «клиент висит, панель 40 мин не трогали → поднимаем» (11.08.2026 постоянный ssh-клиент отменял подъём бессрочно) |
| агента нет, а в панели работает человек — вмешиваться нельзя, молчать нельзя | ветка `сказать` в `решение_по_панели` → сообщение владельцу с кулдауном | селфтест: «владелец печатает, агента нет час → сказать» |
| уйти из сессии можно только вместе с преемником | `session-warden.sh --rotate-now` (выход + подъём + пинок) + запрет голого выхода в `guard_bash.py` | живой цикл смены на одноразовой сессии; 122 пути теста сторожа команд |
| падение любого юнита, смерть cron, перезагрузка сервера | `sentinel.sh` на `harness-sentinel.timer` (systemd) — носитель, независимый от cron; `harness-agent.service` с `Restart=always` | селфтест sentinel + живой случай состаренной метки; полностью — тестовым ребутом |
| пороги — данные | `harness.conf`: `AGENT_DEAD_MIN=15`, `AGENT_DEAD_RESPECT_ATTACHED=1`, `AGENT_ATTACHED_IDLE_MIN=10`, `AGENT_DEAD_COOLDOWN_MIN=120`, `CRON_STALE_MIN=25` | правка порога не требует правки скрипта |
| вход делается СРАЗУ в сессии агента, одной и той же командой запуска | §1.3 ИНСТРУКЦИИ переписан; блок «ОСТАЛОСЬ РУКАМИ» читает `AGENT_START_CMD` и `AGENT_DEAD_MIN` из `harness.conf` | `--dry-run`: напечатанное владельцу и команда сторожа больше не могут разойтись — источник один |
| «где вводить» названо явно: оболочка / ВНУТРИ tmux / ВНУТРИ Claude Code; таблица «что нажали → что произошло» | §1.3 ИНСТРУКЦИИ + шапка блока «ОСТАЛОСЬ РУКАМИ» + 3 симптома в части 3 | читается глазами; пункт «г) убедиться, что агент жив» печатается с реальными путями |

Общее в двух находках вечера: обе беды выглядели зелёными. Кривой путь прошёл
три проверки факта; мёртвый агент прошёл проверку `is-active` и heartbeat.
Проверять надо СВОЙСТВО, ради которого проверка существует: «путь абсолютный»,
а не «каталог есть»; «в панели claude», а не «юнит active».
