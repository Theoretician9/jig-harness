Записано: 08.08.2026, **решение владельца** дословно (00-ВВОДНЫЕ §1.2): «так как
это будет первая сборка то полуавтомат, потом автомат, как только она будет
проверена — на новых серверах сразу автомат».

**когда:** собираюсь выкатывать в прод, ротировать сессию или делать необратимое
(удаление/пересоздание данных, смена секретов); анонс отправлен и тянет начать,
«пока владелец читает».

**цель:** на первой, ещё не доказанной сборке опасные развилки проходят через
владельца; всё остальное агент делает сам — полуавтомат не означает «спрашивать всё».

**Развилки, требующие анонса и подтверждения:**
1. **выкат в прод** (`deploy.sh`, `git push` в главную ветку);
2. **ротация сессии** (session-warden анонсирует сам — команда завершения приходит
   после подтверждения владельца);
3. **необратимые операции**: уничтожение/пересоздание БД и файлов данных, ротация
   секретов, снос контейнеров с данными.

**Как читать подтверждения:** ответы владельца диспетчер канала складывает в
`$LOG_DIR/confirmations.jsonl` (`LOG_DIR` — из `/etc/harness/install.conf`,
по умолчанию `/var/log/harness`). Строка = JSON с временем, текстом анонса и
ответом. Порядок: отправить анонс с однозначным вопросом («выкатываю X — да/нет?»)
→ ждать появления записи с согласием на ИМЕННО этот анонс → только потом действие.
Свежесть проверять по `ts` — согласие вчерашнему анонсу сегодняшний выкат не
разрешает. **Нет записи — нет действия**; молчание = «нет», напомнить можно,
действовать — нельзя.

**Почему:** права широкие с первого дня (разрешения оболочки выключены — владелец
на них не отвечает), безопасность держат гейты и сторожа. Полуавтомат — данные,
не код: `AUTONOMY="semi"` в install.conf; на проверенных сборках новые серверы
стартуют сразу в автомате.

**пересмотр:** переход в автомат — не по ощущению, а по проверке: чек-лист приёмки
пройден, первая задача прогнана через весь цикл, первая ротация доказана живым
переходом. Переход подтверждает владелец; тогда `AUTONOMY="full"` и запись обновить.
