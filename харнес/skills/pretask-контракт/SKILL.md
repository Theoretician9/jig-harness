## 4. Контракт на задачу

**Вход:** задача из плана + реальный код.
**Выход:** машиночитаемый контракт, `харнес/шаблоны-задач/pretask-template.yaml`.
**Готово, когда:** каждый критерий приёмки проверяется командой с однозначным
выводом; либо стоит флаг «спека неполна».

Перед каждой нетривиальной задачей — отдельный проход **анализа без кода**:

```yaml
task_id: <из плана>
tier: <уровень глубины>
acceptance_criteria:      # булевы предикаты, проверяемые тестом или командой
edge_cases:               # случай → ожидаемое поведение
failure_modes:            # что НЕ должно произойти ни при каких условиях
test_plan: {unit, integration, negative}
out_of_scope:             # что задача НЕ делает
known_dependencies:       # соседние модули: видим, но не правим
risk_flags:               # где вероятнее всего сломается
```

Правила прохода: **не писать код, не предлагать реализацию**. «Работает корректно» —
не критерий; «команда X возвращает 0» — критерий. Если задача описана недостаточно —
остановка с флагом «спека неполна», а не додумывание. Ценность контракта — поймать
расхождение между планом и реальным кодом до того, как исполнитель начнёт писать.

Контракт — источник истины для тестов и кода. Менять его по ходу можно один раз,
с пометкой «пересмотрен из v1» и пересмотром уже написанных тестов — иначе критерии
приёмки подгоняются под то, что получилось.

## `pretask.yaml` — контракт задачи

Перед реализацией **отдельный агент-аналитик** (не будущий исполнитель) пишет
`pretask.yaml`: что именно должно стать правдой, какие крайние случаи существуют, чем
задача может сломаться. Шаблон — `харнес/шаблоны-задач/pretask-template.yaml`.

```yaml
task_id: <ID задачи>
tier: T2

acceptance_criteria:
  # ПРОВЕРЯЕМЫЕ КОМАНДОЙ, а не словами
  - "grep -c '<запрещённый паттерн>' <файл> returns 0"
  - "<команда прогона тестов файла> exits 0 with N passed"
  - "<команда полного прогона> exits 0 — no regressions"

edge_cases:
  - case: "В коде НЕТ вызова, который план предлагает удалить — описание плана неверно"
    expected_behavior: >-
      Исполнитель НЕ должен добавлять вызов, чтобы потом его удалить.

failure_modes:
  - "Событие публикуется ДО успеха внешнего вызова: клиент получает
     уведомление о действии, которое затем упало"

test_plan:
  unit: [...]
  integration: [...]
  negative:
    - "Временно убрать вызов → тест обязан покраснеть — подтверждает, что тест реален"

out_of_scope:
  - "<что сознательно не входит — со ссылкой на задачу, куда входит>"

known_dependencies:
  - module: <абсолютный путь>
    why: >-
      Зачем читать. Что именно оттуда нужно.
    modifiable: false      # можно ли править в рамках этой задачи

risk_flags:
  - >-
    HIGHEST — <самое опасное место задачи и почему>.
```

**Ценность контракта:** он ловит расхождения между планом и реальным кодом ДО того, как
исполнитель начнёт писать. Живой пример механизма: план описывал удаление вызова, которого
в коде не было, — без контракта исполнитель добавил бы код, чтобы потом его удалить.

**Ключевое требование к `acceptance_criteria`:** каждый критерий проверяется командой с
однозначным выводом. «Работает корректно» — не критерий. `grep -c ... returns 0` — критерий.

Контракт — это «что должно получиться». Отдельный проход «обо что споткнёмся» (ловушки
конкретной задачи) — другой взгляд и другие находки; он описан в [05-ПАЙПЛАЙН.md].
